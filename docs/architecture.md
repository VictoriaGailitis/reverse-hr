# Архитектура и проектные правила v1

Статус: проект для реализации и проверки. Согласование с командой не заявляется.
Разделение ответственности участников в исходных документах — описание проекта,
а не полномочие отправлять сообщения или создавать дополнительные чаты.

## Владение данными

| Сервис | Собственные бизнес-данные следующего этапа |
|---|---|
| Identity | Локальные ссылки на OIDC subject и внешние идентификаторы; пароли у Keycloak |
| Privacy | Версии согласий, история отзыва, разрешения компаниям, удаление |
| Candidate | Профиль, контакты, резюме, экспорт |
| Employer | Организации, членства, верификация, отзывы, жалобы |
| Assessment | Версии контента, сессии, политика попыток, решения и апелляции |
| Coding Workspace | Файлы, неизменяемые снимки, запросы исполнения |
| Code Runner | Результаты ограниченного запуска; исполнение пока отсутствует |
| Whiteboard | Операции и снимки досок |
| Media | Загрузки, метаданные записей, транскрипты, ссылки на закрытые объекты |
| Proctoring | Наблюдаемые события и проверка самостоятельности |
| Evaluation | Рубрики, версии моделей, оценки, доказательства, проверка человеком |
| Matching | Поисковые проекции без контактов, снимки подборок и объяснения |
| Hiring | Потребности, вакансии, приглашения, отклики, диалоги |
| Achievements | Нормализованные результаты, происхождение и статус доверия |
| Integration | Адаптеры, подключения, доставленные версии и ошибки |
| Notification | Уведомления и предпочтения |
| Audit | Значимые действия и журнал доступа |

У каждого приложения — своя роль и БД; SQL-доступ к другим БД запрещён.
Общий образ приложения сейчас запускает транспортный каркас по `HR_SERVICE_NAME`.
Это не 17 готовых бизнес-сервисов. Domain API реализован у Candidate, Employer, Privacy, Assessment (каталог, планы, preflight), Coding Workspace (черновики/запросы запуска) и Code Runner (приём/техническая диагностика). Миграции доменных таблиц разделены по владельцам в `migrations/domains/`;
общая миграция `0001_transport` создаёт только локальные outbox/inbox
и записи идемпотентности. Изменения домена в общую метадату не добавляются.

## Права первого сценария

| Операция | Авторизация, которую обязан реализовать владелец API |
|---|---|
| Профиль и согласия | Только кандидат с `sub` владельца |
| Создание/отправка сессии | Владелец, действующее согласие, серверный план этапов |
| Подтверждение категории | `assessment_reviewer`, назначенная проверка, причина и доказательства |
| Потребность/подбор | Действующее членство рекрутера/владельца в проверенной организации |
| Приглашение | Рекрутер/владелец этой организации; зарплата обязательна |
| Принятие | Только кандидат, которому направлено приглашение |
| Контакты | Действующее членство и актуальное разрешение этой компании в Privacy |
| Экспорт ATS | Разрешение этой компании и отдельное основание экспорта; повторная проверка перед доставкой |

Членство проверяется сервером Employer, не полем `organization_id` и не одним
realm-role. Технический эксперт организации не получает доступ к контактам по
умолчанию. Роли платформы разделены. JWT должен проверяться по подписи JWKS,
issuer, audience, сроку, разрешённому алгоритму и типу токена. Заголовки с заявленной
ролью/пользователем не заменяют OIDC. JWT и объектные проверки реализованы в трёх
активных API. Межсервисная идентификация, разрешения на раскрытие и удаление впереди.

## Команды, ошибки и переходы

Все бизнес-команды требуют `Idempotency-Key`; ключ scoped по актору и операции.
Повтор с тем же телом возвращает исходный статус/ответ; с другим — `409`.
Для изменения существующего объекта обязателен `If-Match: "<version>"`.
Устаревшая версия — `409 version_conflict`. Изменение и outbox фиксируются вместе.
Исполнение и повтор команд реализованы для текущих доменов; резервирование ключа,
изменение, событие и ответ имеют одну транзакцию. Конкурентный повтор использует
уникальный ключ, конфликт откатывает изменения. Нет внешних действий внутри транзакции.

Ошибка: `code`, безопасное `message`, список полей `fields`, `trace_id`.
`401` — нет валидной аутентификации, `403` — нет разрешения, `404` — объект не
найден/скрыт от актора, `409` — конфликт, `422` — неверные поля,
`503` — зависимость временно недоступна. Контакты при сбое Privacy закрыты.
`X-Request-ID` принимает только UUID или генерируется сервером. Это ID корреляции,
а не полноценная распределённая трассировка OpenTelemetry.

Сессия: `created → preflight → in_progress → submitted → evaluating → review_pending
→ completed`. При сбое — `technical_failure`, затем восстановление исходного этапа
с аудитом. Сам клиент не публикует оценку. Компетентность и самостоятельность —
разные результаты. Публикация категории требует содержательного решения проверяющего.
Неудачное повышение сохраняет грейд; попытка и смена уровня имеют разные таймеры,
смена подтверждённого грейда исходно ограничена 90 днями.

Приглашение: `draft → sent → viewed → accepted/declined/expired/revoked`.
Принятие/отклонение допустимо и непосредственно из `sent`; просмотр не обязателен.
Истечение и отзыв допустимы из `sent/viewed`; принятый статус остаётся в истории,
а доступ может отдельно отозваться в Privacy. Изменённые существенные условия — новая версия.
Зарплата задаётся в RUB за месяц, с явным `gross/net`, положительными границами.

## События и раскрытие

| Событие | Producer | Payload (только UUID) | Потребители |
|---|---|---|---|
| `hiring.invitation_accepted.v1` | Hiring | invitation_id, candidate_id, organization_id, consent_id | Privacy, Notification |
| `privacy.contact_grant_created.v1` | Privacy | grant_id, candidate_id, organization_id | Hiring, Audit |
| `privacy.contact_grant_revoked.v1` | Privacy | grant_id, candidate_id, organization_id | Hiring, Integration, Audit |
| `assessment.grade_confirmed.v1` | Assessment | candidate_id, decision_id | Matching, Notification |
| `integration.ats_export_delivered.v1` | Integration | export_id, candidate_id, organization_id | Hiring, Audit |

Событие включает ID, версию схемы, время, producer, correlation ID и версию агрегата.
Подпись/идентичность producer проверяется транспортом; входящий payload не управляет правами.
Outbox исключает потерю события при атомарном изменении данных. Доставка допускает
повторы; inbox записывается в той же транзакции, что и эффект обработчика.
Передаваемые файлы, контакты и содержимое работ не находятся в событиях.

Hiring фиксирует принятие и событие, Privacy проверяет основание и создаёт
разрешение конкретной компании. Ответ принятия может иметь `contact_access=pending`.
Candidate заново проверяет Privacy при каждом раскрытии. Integration также
проверяет разрешение непосредственно перед отправкой. Отзыв оставляет версионный
след: позднее событие принятия не может восстановить отменённый доступ.
Внутренний consumer Privacy уже реализует эту часть: согласие `contact_disclosure`
блокируется в транзакции, разрешение уникально по приглашению, отзыв сохраняет
запись со статусом revoked. Публичный API даёт только собственный список и отзыв.
Consumer подключён к RabbitMQ, проверяет подпись Hiring и минимальный envelope.
Сам API приглашений Hiring, выдача контактов и ATS пока отсутствуют.

Реализованы publish confirms, ограниченные повторы publisher с backoff, задержка
consumer через quorum retry-очередь, DLQ и административный replay outbox с MFA.
Есть отдельные учётные записи брокера, ACL и подписи Ed25519 для каждого producer.
Сверка порядка событий для будущих проекций и replay consumer DLQ остаются впереди.
Inbox не даёт exactly-once во внешней системе.

## Приёмка последующих этапов

1. Чужой `sub` не читает/меняет профиль, запись или сессию.
2. Чужое `organization_id` и бывшее членство не дают прав на приглашение/контакты.
3. Повторы и конкурентные команды дают один бизнес-эффект или явный конфликт.
4. Контакты отсутствуют в поиске, закрытом PDF, событиях, уведомлениях и логах.
5. Принятие одновременно с отзывом не возвращает доступ; Privacy недоступен — выдачи нет.
6. Неудачное повышение/таймаут модели не понижает грейд и не даёт нулевую оценку.
7. Демообъекты исключены из рабочего рейтинга, real API не обозначается подключённым.
8. Удаление закрывает новые операции и подтверждается владельцами производных данных.
