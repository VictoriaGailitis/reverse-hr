# Proctoring: журнал самостоятельности

Сервис реализует BE-08: собирает материал проверки самостоятельности отдельно
от Evaluation score и подтверждённого грейда. Ни потеря фокуса, ни вставка, ни
остановка записи не означают автоматически нарушение или использование ИИ.

## Допуск и события

До создания потока Proctoring проверяет подписанные ответы Privacy и Assessment:
кандидат, сессия, конкретный активный этап, срок этапа и действующее согласие на
оценку. Подписи Ed25519 разделены контекстами; внутренние endpoints закрыты nginx.
Блокировка кандидата и локальное удаление закрывают операции немедленно.

`POST /v1/proctoring/streams` принимает `session_id`, `stage_id`, случайный
`stream_id`, `client_started_at` с часовым поясом и `Idempotency-Key`.
Поток нельзя перенести между кандидатами или этапами. Новая вкладка/перезагрузка
создаёт отдельный поток; максимум 64 на этап. Восстановление существующего потока
доступно через `GET /v1/proctoring/streams/{id}`; чужой поток недоступен.

`POST /v1/proctoring/streams/{id}/events` принимает `events` (1–50):
`event_id`, `sequence` (1–20000), `kind`, `client_time` с часовым поясом,
`elapsed_ms`. Максимум 20000 событий на этап, включая серверную историю.
При превышении лимита пакет целиком отклоняется, без частичной записи.

Клиентские виды: heartbeat, visibility_hidden/visible, focus_lost/gained, paste,
recording_started/stopped/error, offline/online, telemetry_overflow.
Содержимое буфера, клавиши, адреса страниц и произвольные поля не принимаются.
События неизменяемы; повтор идентичного ID и sequence не увеличивает журнал.
Несовпадающее содержимое при повторе даёт 409. Пакет фиксируется атомарно.

Серверный `ordinal` определяет порядок поступления. Клиентская последовательность
в каждом потоке восстанавливается отдельно; пропуски заполняются без потери
истории. Сохраняются серверное время приёма, заявленное клиентское время и
монотонная длительность. Журнал показывает начальное расхождение часов/доставки,
скачки времени и интервалы между телеметрией более 90 секунд. Эти признаки
обозначают неопределённость, а не доказанное нарушение. За пределами максимальной
принятой sequence неизвестен размер отсутствующего хвоста — журнал не утверждает
полноту наблюдения за клиентом.

После закрытия этапа можно доставить буфер только уже допущенного потока:
такие события отмечаются `late_client_delivery`. Создать новый поток нельзя.
Отзыв согласия, недоступность Privacy/Assessment или tombstone запрещают доступ.

## История сред

Подписанный consumer принимает ссылки на создание/изменение/завершение доски,
создание/перезапуск/финализацию записи и сохранение снимка/запрос запуска кода.
Для Coding Workspace используются отдельные события
`snapshot_saved_observed.v1` и `run_requested_observed.v1`; существующий контракт
Runner не меняется. Текст исходников и медиа в события не включаются.

Проверяются producer, формат этапа, кандидат/сессия/этап и aggregate ID.
Inbox исключает повторную доставку. Уникальная связь вида события, aggregate ID
и версии исключает семантические повторы с новым event ID. Запоздавшие версии
сохраняются как история, без отката текущего состояния. После удаления подписанные
старые события не воссоздают данные. Недоступность зависимостей ведёт в обычный
retry/DLQ, а не создаёт положительный допуск.

## Проверка человеком и Evaluation

Кандидат читает свой журнал; `assessment_reviewer` с MFA читает чужой материал:

`GET /v1/proctoring/candidates/{candidate}/sessions/{session}/stages/{stage}`

Пагинация: `after` — серверный ordinal, `limit` — 1–200. Ответ содержит summary,
страницу событий, `next_after`; summary относится ко всему текущему журналу.
Последующие страницы могут увидеть новые события; итоговое решение проверяется
по версии и SHA-256 всего материала, а не по стабильности отдельных страниц.

`POST .../reviews` требует `Idempotency-Key`, `If-Match` текущей версии и:
`timeline_version`, `evidence_digest`, `outcome` (clear/inconclusive/concern),
`reason` и `evidence_ids`. Concern требует ссылки на существующие события этого
этапа. Самопроверка запрещена. Причина обязательна; новые решения не стирают
старые. Новое событие или поток делает предыдущее решение устаревшим и возвращает
`needs_review`. Нет материала — `no_material`, а не автоматический clear.
Результат не меняет score, grade, Matching или доступ к следующему этапу.

Evaluation получает подписанную свежую summary через
`POST /internal/v1/integrity-summary`: nonce, candidate/session/stage и запрос
строго связаны с ответом, повтор nonce запрещён. Проверяющий читает её через
`GET /v1/evaluations/{stage_id}/integrity` после проверки владельца intake и
Privacy. Работодатель и кандидат не получают reviewer endpoint. Материал
самостоятельности не добавляется автоматически в LLM-оценку компетентности.

## Клиент

`mountProctoring` экспортируется модулем `/proctoring/v1/environment.js` и тем же
модулем практических сред. Контроллер страницы вызывает его один раз на активный
этап каждого формата и показывает `onStatus` пользователю. Полученный объект
передаётся как `proctor` в `mountRecording`, чтобы фиксировать запись/остановку/
ошибку. Listener paste никогда не читает clipboardData.

```javascript
const proctor = await mountProctoring({
  api, sessionId, stageId,
  onStatus: state => showTelemetryStatus(state.status)
});
const unmountRecording = mountRecording(root, {
  api, sessionId, stageId, recordingConsentId, onReady, proctor
});
// До отправки этапа:
const delivered = await proctor.flush();
// При уходе со страницы:
unmountRecording();
await proctor.dispose();
```

`api` предоставляет существующие authenticated JSON requests, включая
Idempotency-Key. Heartbeat — каждые 30 секунд. Создание потока повторяется до трёх раз с неизменным ключом и параметрами.
Повтор доставки сохраняет ID,
sequence и ключ пакета. Буфер: 500 ожидающих плюс до 50 в активном пакете;
переполнение оставляет пропуски и явное техническое событие. Нет локального
хранения телеметрии и фоновой отправки через unauthenticated beacon.
Перезагрузка создаёт новый поток; несохранённые события в памяти теряются, это
ограничение материала. Код клиента можно отключить/подделать, поэтому сервер не
считает его независимым доказательством. При неудачной финальной доставке
контроллер показывает техническую проблему, не объявляет успешное сохранение.
Media и редактируемая Whiteboard автоматически создают поток, если контроллер
не передал общий `proctor`; перед `onReady` требуют успешного flush и снимают
listener/timer при unmount. Для code/SQL контроллер страницы подключает
`mountProctoring` к началу активного этапа. Модуль не внедряется в произвольные
страницы браузера.

## Запуск и Privacy

Миграция `0002_proctoring` создаёт собственные таблицы сервиса; downgrade
запрещён при наличии материала или tombstones. Compose profile `all` включает
API, `proctoring-consumer` и `proctoring-outbox` с отдельными credentials.
После изменения topology оператор запускает `scripts/configure_events.py` и
загружает обновлённые definitions в RabbitMQ по существующей процедуре.

Privacy удаляет потоки, события, ручные решения, ответы команд и outbox; сохраняет
только ограничение против восстановления и подписанный ACK. При удалении
проверяющего удаляются его решения/свободный текст, статус соответствующей
проверки возвращается к ожиданию. Очистка копий в Audit/backup — ответственность
их владельцев и общей процедуры Privacy, а не дополнительный локальный архив
Proctoring.

Локальные API/integration-тесты используют реальные подписи и миграции SQLite;
устройства браузера, PostgreSQL/RabbitMQ и полный Compose требуют отдельного
живого прогона.
