## Локальная проверка без Docker

Требуются Python 3.12/3.13 и uv. SQLite используется для локальных тестов;
стенд работает с PostgreSQL.

```sh
uv sync --frozen
uv run pytest -q
uv run ruff check .
uv run ruff format --check .
PYTHONPATH=src uv run python scripts/export_contracts.py
```

Для локальных API сначала подготовьте .env через scripts/configure.py, если его
ещё нет, и ключи через configure_events.py. Candidate/Employer/Assessment/Coding Workspace/Code Runner/Evaluation требуют
работающий Privacy; запуск одного Candidate достаточен только для health/docs.

В первом терминале запустите Privacy:

```sh
export PYTHONPATH=src
uv run python scripts/configure_events.py
export HR_SERVICE_NAME=privacy
export HR_DATABASE_URL=sqlite:///./privacy.db
uv run python -m reverse_hr.migrate upgrade head
uv run uvicorn reverse_hr.app:create_app --factory --port 8002 --no-access-log
```

Во втором терминале запустите Candidate:

```sh
export PYTHONPATH=src
export HR_SERVICE_NAME=candidate
export HR_DATABASE_URL=sqlite:///./candidate.db
export HR_PRIVACY_API_URL=http://127.0.0.1:8002
uv run python -m reverse_hr.migrate upgrade head
uv run uvicorn reverse_hr.app:create_app --factory --port 8001 --no-access-log
```

Для пользовательских запросов также нужен действующий Keycloak access token.
Локальные быстрые тесты сами создают временные ключи и подменяют JWKS источник.

## Демостенд

```sh
python3 scripts/configure.py
PYTHONPATH=src uv run python scripts/configure_events.py
docker compose config --quiet
docker compose up --build -d
```

Генератор создаёт `.env` с независимыми случайными секретами и правами 0600;
существующий файл не перезаписывается. Не копировать `.env.example` вместо генерации.
В стандартном режиме запускаются Candidate, Employer, Privacy, Assessment, Coding Workspace, Code Runner и Evaluation плюс инфраструктура.
Если registry недоступен, проверяйте код локально; запуск контейнеров требует
предварительной загрузки образов. S3 вынесен в профиль `storage` (образ пока не удалось загрузить):
`docker compose --profile storage up -d minio`.
Остальные каркасы включаются через `docker compose --profile all up --build -d`.

Gateway: `http://localhost:8000`. Swagger: `/candidate/docs`, `/privacy/docs`,
`/employer/docs`, `/assessment/docs`, `/coding-workspace/docs`, `/code-runner/docs`,
`/evaluation/docs`. Health: `/candidate/health/live` и `/candidate/health/ready`.
Keycloak: `http://localhost:8080`, realm `reverse-hr`; административный логин
`local-admin`, пароль берётся из локального `.env`.

Каждый сервис получает свою БД и роль. Скрипт инициализации исполняется только
при первом создании тома PostgreSQL. Изменение секретов в `.env` **не** меняет пароли
в уже созданной БД. Для ротации нужна отдельная управляемая операция.

Контейнеры приложений работают непривилегированно, с файловой системой только для
чтения; БД, Redis, RabbitMQ и S3 не публикуются на хост. Это локальная конфигурация:
Keycloak работает в `start-dev`; TLS ещё не настроен. SMTP и MFA описаны в конфигурации ниже, их запуск на Keycloak пока не подтверждён. Реальные
персональные данные на текущем этапе не загружать.


## Identity: локальная почта и MFA

Realm `infra/keycloak/realm.json` включает регистрацию, подтверждение email,
восстановление пароля, защиту перебора и пароль минимум 12 символов с цифрой,
верхним и нижним регистром. Приложение использует Authorization Code + PKCE S256:
password grant, implicit flow и service accounts для `reverse-hr-web` выключены.
Редирект разрешён только на `http://localhost:3000/auth/callback`.

Письма направляются в Mailpit по внутренней сети, интерфейс просмотра доступен
только на `http://localhost:8025`. SMTP не опубликован на хост; пересылка наружу
не настроена. Почта временная (tmpfs, максимум 200 сообщений). Используйте только
синтетические адреса `@reverse-hr.invalid` на этом стенде. Это тестовый приёмник,
реальный SMTP и шаблоны/доставка ещё предстоят.

Роли `company_moderator`, `assessment_reviewer`, `content_admin`, `technical_admin`
включают `requires_mfa`; саморегистрация даёт только candidate. Поток `hr-browser`
проверяет пароль и требует OTP у этих ролей, включая первичную настройку TOTP.
Для обычного пользователя уже настроенный OTP также проверяется. Поток не
использует cookie shortcut: каждый новый вход проходит пароль и применимый OTP.
После первой настройки OTP для привилегированного API может потребоваться новый
вход, чтобы токен содержал подтверждение фактически пройденного OTP шага.

AMR mapper получает `pwd`/`otp` от выполненных authenticator executions; условие
роли не помечается как MFA. Срок AMR — 900 секунд, access token — 300 секунд,
refresh tokens ротируются без повторного использования. Если обновлённый токен
уже не содержит MFA, привилегированный API отвергает его, нужен новый вход.
Механизм сверён с исходниками
[AMR mapper Keycloak 26.3.3](https://github.com/keycloak/keycloak/blob/26.3.3/services/src/main/java/org/keycloak/protocol/oidc/mappers/AmrProtocolMapper.java).

Startup import применяется к новому realm. Уже существующий realm при перезапуске
[пропускается Keycloak](https://www.keycloak.org/server/importExport); эти изменения
не мигрируют существующие аккаунты автоматически. Применение к существующему realm
через Admin API и проверка регистрация → письмо → подтверждение → восстановление
ещё предстоят. Не удаляйте существующий realm или том БД для применения настроек.

Добавлены opt-in проверки `tests/test_identity_live.py`: они импортируют уникальный
временный realm `hr-test-<UUID>`, создают только синтетических пользователей,
проверяют настоящий PKCE-вход, подпись/claims токена и OTP, затем удаляют только
свой тестовый realm. Пароль администратора задаётся исключительно переменной
`HR_TEST_KEYCLOAK_ADMIN_PASSWORD`, не аргументом командной строки. Не выводите его.
Необязательные настройки: `HR_TEST_KEYCLOAK_URL` (только loopback HTTP origin) и
`HR_TEST_KEYCLOAK_ADMIN_USER` (по умолчанию local-admin).

После подготовки этих переменных и запуска локального Keycloak:

```sh
PYTHONPATH=src uv run pytest -q tests/test_identity_live.py --tb=short
```

Тестовые аккаунты подтверждаются администратором для проверки OAuth/MFA; этот
набор не заменяет проверку доставки и перехода по настоящему email verification.
Пока Docker недоступен, live Keycloak тесты остаются пропущенными, и работоспособность
realm на сервере не объявляется подтверждённой.

## Доступ и команды этапа 3

Для API требуется Bearer access token Keycloak: RS256, корректные issuer/audience,
срок действия, `typ=Bearer`, UUID в `sub` и `email_verified=true`. Параметры задаются
через `HR_OIDC_ISSUER`, `HR_OIDC_AUDIENCE`, `HR_OIDC_JWKS_URL`; в Compose URL JWKS
внутренний, а issuer остаётся `http://localhost:8080/realms/reverse-hr`.
Проверка сверена с [PyJWT](https://pyjwt.readthedocs.io/en/stable/usage.html).
Локальные тесты подписывают JWT одноразовым RSA-ключом и подменяют только источник
JWKS; подпись и проверки claims выполняются настоящим verifier.

Кандидат с ролью `candidate` создаёт профиль `POST /v1/candidates/me`, читает
`GET /v1/candidates/me`, изменяет `PUT /v1/candidates/me`. Подтверждённый грейд
ещё не вычисляется и остаётся `null`; прислать его с клиента нельзя.

Работодатель с ролью `employer` создаёт организацию и становится её владельцем.
Чтение требует реального членства. Только владелец добавляет сотрудников по
известному OIDC subject, роли `recruiter`/`technical_expert`; перенос владения,
приглашения сотрудников и проверка существования subject в Identity пока впереди.
Компания создаётся в статусе `pending`. Решение модератора требует роли
`company_moderator` и подписанного `amr`, содержащего `mfa` или `otp`.
Настройка flow MFA и AMR mapper в Keycloak ещё не проверена; без AMR API отказывает.

Согласия доступны только своему кандидату: список `GET /v1/consents`, выдача
`POST /v1/consents`, отзыв `POST /v1/consents/{id}/revoke`. Технические версии
демополитик можно получить через `GET /v1/consents/policies`: сейчас `demo-v1`.
Это идентификаторы технического прототипа, не юридически проверенные тексты.
Новый ключ команды выдачи создаёт отдельное подтверждение; отзыв конкретного ID
не отзывает другие подтверждения. Проверка применимого основания перед обработкой
медиа/ATS и каскадный отзыв разрешений добавляются вместе с этими сервисами.

Все изменяющие команды требуют `Idempotency-Key`; изменения существующих объектов
также `If-Match: "1"` с текущей версией. Повтор одинаковой команды возвращает
сохранённый ответ, другой payload с тем же ключом и устаревшая версия дают `409`.
Согласие хранит время, subject и версию документа. Изменения и outbox-события
фиксируются одной транзакцией; publisher и транспорт запускаются отдельными worker.
Контакты хранятся только в Candidate и выдаются через Hiring после принятия приглашения
и проверки действующего разрешения Privacy. Импорт резюме, изолированный PDF/OCR,
подтверждение полей, экспорт полного/обезличенного PDF и очистка Candidate
реализованы: [резюме и PDF](resume-pdf.md).

## История и отзыв доступа

Employer сохраняет каждое новое решение модератора в `verification_decisions`:
проверяющий, причина, источник `manual_review`, время и версия организации.
`GET /v1/organizations/{id}/verification-history` доступен владельцу и модератору
с MFA. Новое решение не заменяет предыдущие. Состояние компаний, записанное до
миграции 0003, остаётся в карточке без искусственно созданных исторических решений.

Владелец отзывает сотрудника через
`POST /v1/organizations/{org}/members/{membership}/revoke`. `If-Match` здесь —
версия членства; остальные команды организации используют версию организации.
Отзыв повышает обе версии. Владелец не может отозвать самого себя; перенос
владения реализуется отдельно. Отозванное членство сохраняется. Действующий JWT
не возвращает доступ. Повторное добавление того же subject пока даёт конфликт;
восстановление членства впереди.

Privacy предоставляет кандидату `GET /v1/contact-grants` и
`POST /v1/contact-grants/{grant}/revoke` с версией разрешения в `If-Match`.
Публичного создания разрешений нет. Внутренний `process_accepted_invitation`
вызывается аутентифицированным транспортом Hiring: он требует
ссылки на кандидата, компанию, приглашение и действующее согласие
`contact_disclosure` версии `demo-v1`. Проверка поля producer внутри функции
не заменяет проверку личности сервиса транспортом. Worker Privacy подключён к
RabbitMQ и проверяет подпись Hiring; бизнес-API приглашений описан ниже.

Inbox, разрешение и исходящее событие фиксируются атомарно. Приглашение может
создать только одно разрешение. Повтор/позднее событие не заменяет отозванную
запись; истечение также не продлевается повтором. Срок берётся от времени принятия,
демополитика — 30 дней (параметр обработчика, диапазон 1–365). Слишком старое или
будущее событие блокируется. Эта политика требует продуктового согласования до
пилота. Согласие блокируется в БД на время создания разрешения; его отзыв закрывает
все связанные разрешения в одной транзакции.

`permitted_contact_grant` проверяет конкретную компанию, срок, статус разрешения
и согласия. Это внутренний механизм Privacy; работодателю не открыт HTTP-маршрут
проверки/выдачи контактов. ATS требует своего основания экспорта. Полная очистка данных,
очистка проекций, доставка событий и проверка членств между сервисами ещё впереди.

Реализация lifecycle сверена с [FastAPI](https://fastapi.tiangolo.com/advanced/events/),
порядок запуска — с [Docker Compose](https://docs.docker.com/compose/how-tos/startup-order/),
локальная конфигурация Identity — с [Keycloak](https://www.keycloak.org/server/containers).

## Транспорт событий

После `configure.py` выполните `PYTHONPATH=src uv run python scripts/configure_events.py`.
Команда сохраняет ключи Ed25519, публичный keyring и определения RabbitMQ в
`.secrets/`, а отдельные пароли AMQP — в `.env`. Повтор сохраняет существующие ключи
и пароли. Каталог имеет права 0700; каждый worker получает только собственный
закрытый ключ и общий публичный keyring. Каталог исключён из Git и Docker context.
Ротация ключей с поддержкой сообщений в полёте ещё не реализована.

`docker compose --profile events up --build -d` включает publisher Candidate,
Employer, Privacy, Assessment, Coding Workspace, Code Runner и consumers Privacy/Candidate/Employer/Assessment/Coding Workspace/Code Runner.
Matching/Hiring publisher и consumer включаются профилем `all`. Для локального worker задайте `HR_SERVICE_NAME`,
`HR_DATABASE_URL`, `HR_AMQP_URL` и пути к файлам ключей, затем запустите
`python -m reverse_hr.worker publish` либо `python -m reverse_hr.worker consume`.
Consumers реализованы для Privacy, Candidate, Employer, Assessment, Coding Workspace,
Code Runner, Matching, Hiring и Notification.

Publisher берёт одну запись outbox под блокировкой PostgreSQL `SKIP LOCKED`,
подписывает её и отправляет persistent message с mandatory routing и confirms.
После подтверждения записывается `published`; сбой даёт ограниченный повтор с
экспоненциальной задержкой, затем статус `dead`. Потеря соединения после приёма
брокером, но до commit, может повторить доставку. Это штатная at-least-once семантика.
Один publisher поддерживается в SQLite; конкурентные workers требуют PostgreSQL.

У каждого сервиса отдельный пользователь RabbitMQ: он пишет только в собственные
exchanges и читает свои очереди. Topology создаётся из definitions, сервисы не имеют
configure-прав. Все события сохраняются также в очереди Audit; её бизнес-обработчик,
сроки хранения и очистка backlog пока впереди. Broker admin не передаётся workers.

Privacy проверяет Ed25519-подпись, допустимый источник Hiring, тип события, ID и
схему до начала бизнес-транзакции. Inbox, разрешение и outbox фиксируются вместе;
ACK отправляется после commit. Временная ошибка уходит в quorum retry-очередь
с задержкой 5 секунд. TTL возвращает её в incoming с at-least-once dead-letter policy.
Повторы ограничены, окончательная ошибка идёт в DLQ. Если перенос не подтверждён,
исходное сообщение остаётся unacked. Повтор подтверждённого переноса возможен;
inbox предотвращает повторный бизнес-эффект. Для непроверенной подписи сохраняется
только безопасный код ошибки, исходное недоверенное содержимое не сохраняется в DLQ.
Основные механизмы сверены с [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms)
и [RabbitMQ TTL](https://www.rabbitmq.com/docs/ttl).

Повтор `dead` записи outbox доступен через локальную административную команду:

```sh
PYTHONPATH=src uv run python -m reverse_hr.replay EVENT_UUID \
  --key COMMAND_UUID --reason "Причина технического исправления" --token-file /path/to/token
```

Нужен валидный OIDC access token `technical_admin` с MFA и доступ к секретам
конкретного сервиса. Событие проверяется как собственное, ID не меняется. Причина,
оператор, время и результат сохраняются атомарно в журнале команд
`idempotency_records`. Повтор команды с тем же ключом не сбрасывает новые попытки.
Это ещё не отдельный защищённый Audit-сервис. Replay consumer DLQ пока отсутствует.

Полный интеграционный прогон на одноразовом локальном стенде:

```sh
docker compose -f compose.yaml -f compose.test.yaml up -d --wait postgres rabbitmq
PYTHONPATH=src uv run python scripts/integration_tests.py
docker compose -f compose.yaml -f compose.test.yaml stop postgres rabbitmq
```

`compose.test.yaml` временно публикует только localhost-порты 55329 и 55330.
Скрипт читает секреты из `.env`, не выводит их и включает короткий traceback.
Тесты создают синтетические записи; используйте отдельный тестовый volume.
CI настроен на этот же PostgreSQL/RabbitMQ прогон. Его удалённый запуск не проверен.
TLS/mTLS, managed secret store, ротация, мониторинг workers и consumer DLQ replay
остаются следующими эксплуатационными работами.


## Запросы удаления: координатор Privacy

`POST /v1/deletion-requests` с OIDC ролью `candidate` и `Idempotency-Key`
возвращает `202` и единый запрос для собственного subject.
`GET /v1/deletion-requests/me` возвращает текущее состояние. При повторе того же
ключа POST возвращает исходный ответ; для актуального прогресса используйте GET.
Другой ключ не создаёт второе удаление для того же subject.

Privacy в одной транзакции устанавливает постоянный запрет обработки, отзывает
все активные согласия и разрешения, создаёт задания для 17 владельцев данных и
outbox `privacy.deletion_requested.v1`. Новые согласия, поздние принятия
приглашений и повтор старой команды выдачи после ограничения дают `409`.
Блокировка общей строки subject сериализует выдачу согласий/разрешений с удалением
на PostgreSQL; inbox, изменения и события сохраняются атомарно.

Сервис подтверждает очистку собственным подписанным `{service}.data_deleted.v1`,
а незавершённую очистку с ограничением — `{service}.data_restricted.v1`:
aggregate_id = request_id, aggregate_version = 1, payload содержит только
request_id и candidate_id. Consumer проверяет подпись, producer, exchange,
точный запрос/subject и время события; повторы безопасны. Публичного HTTP API
подтверждения нет. RabbitMQ маршрутизирует запрос всем внешним владельцам данных,
а подтверждения — в Privacy. После изменения topology запустите configure_events.py
и перезапустите тестовый RabbitMQ для загрузки definitions.

Это координатор, а не законченная физическая очистка: обработчики удаления в
Identity/Keycloak и остальных сервисах ещё не реализованы. Их задания
остаются `pending`; собственное состояние Privacy — `restricted`, поскольку
его записи сохраняются до подтверждений всех внешних владельцев. Privacy блокирует операции сразу; Candidate и Employer проверяют subject
в Privacy до допуска нового пользовательского запроса. Остальные сервисы ещё
предстоит подключить. Общий статус остаётся
`in_progress`; `completed` требует подтверждений `deleted` от всех 16 внешних владельцев и
собственной атомарной очистки Privacy; результат имеет completed_at.
Нельзя подтверждать очистку, пока остались производные данные, очереди, файлы или
не определены правила сохранения по другому основанию. Backup expiration и
повторное применение реестра удалений после восстановления ещё не реализованы.
Миграция 0004 отказывает в downgrade, если реестр содержит запросы: удаление
ограничений не должно незаметно разрешать повторное создание данных.


## Очистка Candidate

Профиль events запускает `candidate-consumer`, который принимает только
подписанное Privacy событие `privacy.deletion_requested.v1` из разрешённого
exchange. В одной транзакции он удаляет `candidate_profiles` и все собственные
`idempotency_records` данного subject, сохраняет ограничение в
`candidate_subjects`, inbox и outbox `candidate.data_deleted.v1`. Publisher
Candidate отправляет подтверждение в Privacy; consumer ACK следует после commit.
Повтор с тем же event_id не повторяет эффект; новое event_id того же запроса
повторяет очистку без второго подтверждения. Чужой producer, несовпадающий
request_id и будущее событие отвергаются. Задание работает и без существующего
профиля. POST/PUT/GET профиля после очистки дают `409`, включая старый ключ команды.

Строка subject блокируется при командах, чтении и удалении. Поэтому конкурирующая
команда либо завершается до очистки, либо отклоняется. Старый JWT не снимает запрет.
Migration 0003 не разрешает downgrade при сохранённых ограничениях удаления.
До доставки события физический профиль ещё существует, но новый пользовательский
запрос к Candidate проверяет актуальное ограничение в Privacy и отклоняется.

Сохраняются UUID запроса/subject, время и технические inbox/outbox события без
полей профиля. Это служебный реестр, а не полное удаление всех следов системы.
Копии событий в очередях/Audit и downstream проекции требуют собственных
обработчиков и должны применять запрет даже при позднем profile_created.
Candidate также удаляет приватные PDF, текст импорта, черновики и резюме до ACK;
API и consumer должны использовать общий том `candidate-resumes`. Восстановление
резервных копий должно повторно применять удаления
отдельной процедурой: повтор сообщения с уже сохранённым inbox эту процедуру
не заменяет. Глобальный статус Privacy остаётся in_progress.


## Ограничение данных в Employer

`employer-consumer` обрабатывает подписанный запрос Privacy. В одной транзакции
он блокирует subject, отзывает все его активные членства (включая owner), повышает
версии членств/организаций, очищает собственные ответы команд и ответы других
акторов, содержащие этот subject, и записывает inbox/outbox подтверждения.
Повторы не создают второе подтверждение. Создание компаний и повтор старой
команды блокируются. Добавление сотрудника блокирует actor и target в стабильном
порядке; отозванный/удаляемый subject нельзя добавить снова.

Компания и членства других сотрудников сохраняются. Ограниченные членства
не выдаются через список сотрудников; история ограниченного модератора скрыта
через обычный API, а verified_by и verification_reason в текущем решении скрыты.
Хранящиеся записи не объявляются удалёнными: если найдены членства, ссылка
verified_by или история модератора, Employer отправляет `data_restricted`, Privacy
показывает `restricted`, общий процесс остаётся `in_progress`. Когда таких записей
нет, отправляется `data_deleted` после очистки ответов команд. Позднее restricted
подтверждение не понижает уже подтверждённый deleted.

Для retained записей ещё нужны решение об основании/сроке хранения и процедура
окончательной очистки. При отзыве owner новый владелец автоматически не назначается;
управление восстанавливается отдельной командой модератора (см. ниже). Имена компаний
и записи организации остаются общими данными компании и не очищаются автоматически.
Employer проверяет subject пользовательского запроса и target добавления сотрудника
в Privacy; событие затем применяет локальный отзыв и ограничение записей. Migration 0004 защищает существующие ограничения от downgrade.
Обновлённую RabbitMQ topology нужно сгенерировать configure_events.py и загрузить
перезапуском локального тестового RabbitMQ.


## Восстановление владельца компании

`POST /v1/organizations/{organization_id}/ownership-recovery` доступен роли
`company_moderator` с MFA. Тело: `membership_id` существующего сотрудника и
непустая `reason` (до 2000 символов); обязательны `Idempotency-Key` и `If-Match`
с текущей версией организации. Новый владелец должен иметь активное членство
именно в этой компании и актуальный допуск Privacy. При недоступности Privacy
команда отклоняется. Активного владельца таким способом заменить нельзя:
предыдущий owner должен быть отозван после локального запроса удаления Privacy.

В одной транзакции активный сотрудник получает роль owner, прежнее отозванное
членство переводится в recruiter, повышаются версии обоих членств и компании,
сохраняются решение модератора, причина и событие `employer.ownership_recovered.v1`.
Событие содержит только UUID компании и решения. Повтор команды не создаёт
второе решение, но заново проверяет ограничения модератора и нового владельца.

Migration 0005 добавляет закрытую таблицу `ownership_recoveries`; downgrade с
непустой историей запрещён. Ограничение прежнего пользователя остаётся в силе,
его членство и история решения сохраняются, подтверждение Employer остаётся
`restricted`. Это восстановление управления компанией, а окончательная очистка
и правила хранения этих записей остаются отдельной работой. Удаление модератора,
записанного в истории восстановления, также даёт `restricted`.


## Синхронная проверка ограничений Privacy

Candidate и Employer проверяют subject каждого OIDC-аутентифицированного запроса
до выполнения доменной операции, включая чтение и replay сохранённого ответа.
Добавление сотрудника дополнительно проверяет target subject. После commit запроса
удаления новые проверки отклоняются `409` до доставки события. Недоступность Privacy,
таймаут, неверная подпись или неподходящий ответ дают `503`; разрешения не кешируются.
Публичные ответы API помечаются Cache-Control: no-store.

Внутренний `POST /internal/v1/processing-status` принимает только запросы
Candidate/Employer/Assessment, подписанные Ed25519 своим сервисным ключом. Содержит subject,
requester, одноразовый UUID nonce и issued_at. Privacy возвращает подписанный boolean
allowed с теми же subject/requester/nonce. Криптографические контексты запросов,
ответов и событий различаются; JWT пользователя в Privacy не пересылается.
Freshness — 30 секунд; nonce сохраняется 60 секунд в собственной БД Privacy,
повтор отвергается, истёкшие nonce очищаются при следующих запросах. Migration 0005
создаёт replay ledger; readiness проверяет наличие этой таблицы. При существующих
удалениях downgrade блокируется до изменения схемы.

`HR_PRIVACY_API_URL` — фиксированный HTTP(S) origin, по умолчанию http://privacy:8000.
Пути, query, fragment и credentials в нём запрещены. Клиент не следует редиректам,
не использует системный proxy, ограничивает ответ 4096 байтами и задаёт сетевой
таймаут 3 секунды. API контейнеры получают только свой signing key и публичный
keyring. Gateway отклоняет /privacy/internal/; внутренняя подпись всё равно обязательна.
Перед запуском требуется configure_events.py. Production TLS/mTLS, key rotation,
долговременный secret manager и полный запуск API контейнеров ещё предстоит проверить.

Это проверка допуска по subject запроса и target добавления сотрудника, а не
общая транзакция 17 БД. Запрос, проверенный до commit удаления, может завершиться
после него: его результат закрывают локальные tombstones и обработчики удаления.
Структурированные ссылки на сотрудников и модераторов в Employer проверяются
перед выдачей ответа; будущие сервисы и остальные проекции ещё требуют подключения.
Массовое обновление всех проекций этим протоколом не выполнено.
Доступность Candidate/Employer/Assessment теперь зависит от Privacy: обхода проверки или
fallback allow в runtime нет. Доменные unit/DB тесты явно подменяют checker;
отдельные тесты проверяют настоящие подписи и HTTP с PostgreSQL.


## Проверка данных других людей в Employer

При чтении списка сотрудников, карточек компаний и истории модерации Employer
проверяет ограничения subject каждой выдаваемой структурированной ссылки.
Restricted сотрудники и решения скрываются; verified_by и verification_reason
ограниченного модератора возвращаются null, даже если consumer ещё не запущен.
Остальные сотрудники/решения остаются видимыми. Несколько ссылок на одного человека
проверяются один раз внутри текущего HTTP запроса; следующий запрос проверяет снова.
Это не общий кеш разрешений.

Те же правила применяются к сохранённым ответам изменяющих команд: старый revoke
не возвращает subject уже ограниченного сотрудника, а поля ограниченного модератора
редактируются при выдаче. Эффект команды не повторяется; первоначальный ответ в БД
очищается consumer отдельно. При невозможности проверить третье лицо возвращается
503 без частичного списка. Ошибка проверки новой команды откатывает её изменения,
outbox и запись идемпотентности.

Это закрывает известные структурированные ссылки текущего Employer API. Произвольный
текст причины/имени компании не разбирается на персональные данные автоматически;
правила его обработки и окончательная очистка остаются отдельной работой.
Операции, допущенные до commit ограничения Privacy, всё ещё относятся к обработке
в полёте; протокол не обеспечивает общую транзакцию всех БД.


## Финальная очистка Privacy

После `deleted` от всех внешних владельцев данных Privacy в той же транзакции
обработки последнего ACK удаляет ConsentRecord, ContactGrant и сохранённые ответы
команд данного subject (кроме request_deletion), а также свои устаревшие
consent/grant outbox события в любом статусе. Записи другого кандидата не затрагиваются.
Затем сохраняет completed_at, собственный target deleted и outbox
privacy.data_deleted.v1 / privacy.deletion_completed.v1. ACK брокеру следует после
commit. Повтор не создаёт второе завершение. Missing target, pending или restricted
не позволяют завершить очистку; Privacy self-ACK не принимается вместо очистки.

Остаются постоянный запрет обработки, реестр запросов/подтверждений, технический
inbox и события протокола удаления. Запрет не снимается после completed:
новое согласие и поздний hiring event не возвращают доступ. GET прогресса показывает
актуальные completed_at/services. POST с прежним ключом всё ещё возвращает исходный
ответ команды, поэтому для прогресса используйте GET. Migration 0006 добавляет
completed_at и блокирует downgrade непустого реестра. Финализация сериализуется
строкой subject; два последних ACK не создают два события завершения.

Completed здесь — техническое завершение активной очистки по подтверждениям
владельцев, а не доказательство истечения резервных копий или нормативной приёмки.
Обработчики всех внешних сервисов ещё не реализованы; реальные задания пока могут
оставаться pending/restricted. Прогоны завершения используют синтетические ACK
для проверки координатора. Правила хранения реестра и backup restore ещё впереди.

Если Docker недоступен, а PostgreSQL уже установлен и initdb/pg_ctl доступны в PATH:

```sh
PYTHONPATH=src uv run python scripts/local_postgres_tests.py
```

Скрипт создаёт отдельный временный кластер в /tmp на свободном localhost-порту,
с независимыми случайными паролями и тремя тестовыми БД/ролями. Не читает .env и не
использует существующий кластер. Проверяет PostgreSQL и настоящий HTTP, пропускает
RabbitMQ, останавливает и удаляет только собственный кластер. Требует POSIX окружение
и свободное место; ничего не устанавливает. При невозможности остановки сохраняет
свой каталог для восстановления. Полный broker прогон остаётся integration_tests.py.


## Assessment: каталог практического контента

Первый рабочий модуль Assessment — закрытый каталог demo-контента. Все методы
требуют `content_admin` с MFA и актуальный signed processing-status Privacy.
Кандидатам и работодателям каталог недоступен: в версиях хранятся эталоны и рубрики.

| Метод | Назначение |
|---|---|
| `POST /v1/content-families` | Семейство и первая draft-редакция: `name`, `content` |
| `GET /v1/content-families/{family_id}` | Метаданные и текущий счётчик редакций семейства |
| `POST /v1/content-families/{family_id}/versions` | Новая редакция с If-Match семейства |
| `GET /v1/content-versions/{revision_id}` | Содержимое и текущий статус редакции |
| `POST /v1/content-versions/{revision_id}/publish` | Публикация другим администратором с причиной и If-Match редакции |
| `POST /v1/content-versions/{revision_id}/retire` | Снятие опубликованной редакции с причиной и If-Match редакции |

Команды используют `Idempotency-Key`. Содержимое сохранённой редакции не меняется:
исправления создают новую редакцию и UUID. Отдельный счётчик семейства назначает
номер новой редакции; версия самой редакции меняется только при публикации и
снятии. Повтор команды возвращает её первоначальный ответ, GET — актуальное
состояние. Снятая редакция сохраняется и не может быть опубликована повторно.

Пакет содержит специализацию, целевой грейд, ID/версию исходного набора,
`demo: true`, компетенции и практические задания. Форматы: code, sql, vcv, voice,
whiteboard. Каждое задание содержит инструкцию, длительность, эталон и рубрику:
ключ критерия, компетенцию, описание, баллы и тип доказательства. Сервер проверяет
уникальные ключи, полное покрытие компетенций, сумму ровно 100 баллов на задание,
соответствие типа доказательства формату, длительность пакета до двух часов и
размер до 256 КиБ. Non-demo пакеты пока запрещены.

Публикацию выполняет другой content_admin после содержательной проверки. Причина
и ссылки на авторов решений остаются внутри БД Assessment; события содержат только
UUID редакции/семейства. Это публикация контента, она не назначает грейд кандидату.
Тестовые пакеты синтетические и не считаются проверенным набором участника №3.

Migration 0002_assessment добавляет content_families/content_revisions; downgrade
непустого банка запрещён. Gateway выдаёт API под `/assessment/`, отдельный publisher
assessment-outbox включён профилем events/all. Повторы и новые команды закрываются
после ограничения пользователя в Privacy. Планы и preflight-сессии описаны ниже. Окончательная очистка авторских ссылок,
генерация, Runner-проверка вариантов и содержательная оценка результатов ещё впереди.


## Assessment: планы и preflight-сессии

`POST /v1/assessment-plans` принимает `name`, список `revision_ids` и причину
проверки `reason`. Content_admin с MFA создаёт фиксированную demo-версию плана
из опубликованных редакций одного грейда/специализации. Порядок ID задаёт порядок
этапов; все задания выбранных редакций включаются в план. Повторяющиеся ID,
черновики/снятые редакции, смесь уровней, больше 20 заданий или двух часов запрещены.
Редактирования плана нет: изменения получают новый plan_version_id.

Кандидат получает доступные метаданные через `GET /v1/assessment-plans`: название,
специализацию, грейд, длительность и форматы. Эталонов, рубрик и авторских ссылок
в этой выдаче нет. Снятие плана — `POST /v1/assessment-plans/{id}/retire` с причиной,
Idempotency-Key и If-Match его текущего статуса. Снятие контента или плана закрывает
создание новых сессий, сохраняя уже созданные снимки.

`POST /v1/assessment-sessions` принимает только `plan_version_id` и
`assessment_consent_id`. Кандидат определяется по JWT; нельзя передать чужой ID,
выбрать статус или назначить грейд. Privacy через подписанный внутренний запрос
проверяет владельца согласия, purpose assessment, active/demo-v1 и отсутствие
блокировки. Запрос/ответ привязаны к consent_id, subject, requester и nonce;
контексты подписей отделены от processing-status, разрешение не кешируется.
Ошибки проверки закрывают создание и replay (409/503).

Сессия фиксируется как preflight и содержит публичные инструкции со стабильными
stage_id. В снимке нет рубрик/эталонов. Одновременно разрешена одна preflight либо
in_progress сессия на кандидата; это техническое ограничение, а не политика попыток.
`GET /v1/assessment-sessions/{id}` доступен только владельцу с актуальным согласием.
Replay создания возвращает текущий статус сохранённой сессии, сохраняя её ID.

Отмена — `POST /v1/assessment-sessions/{id}/cancel` с Idempotency-Key/If-Match.
Она разрешена после отзыва assessment-consent, но возвращает только метаданные
без инструкций. Общая блокировка пользователя в Privacy закрывает все операции.
Другой кандидат получает 404 при чтении/отмене чужой сессии.

Migration 0003_assessment хранит планы, сессии и tombstones. Assessment consumer
атомарно удаляет сессии и ответы команд subject, сохраняет постоянное ограничение,
inbox и UUID-only подтверждение; ACK брокеру выполняется после commit. При наличии
истории авторства/проверки контента или планов подтверждает restricted, иначе deleted.
Сроки/основания хранения этих технических ссылок и backup restore ещё предстоят.

Для code/SQL добавлены серверные start/stage-start/submit и подтверждение снимков,
описанные ниже. Media/VCV/whiteboard, Evaluation, дополнительные recording-согласия,
назначение грейда, cooldown и апелляции впереди. Материалы и планы demo;
подтверждённую категорию они не меняют.
Нормативная матрица согласий остаётся отдельной работой.


## Coding Workspace: подготовительные версии (BE-06)

`POST /v1/workspaces` принимает session_id, stage_id и полный список files
(path/content). Candidate определяется по JWT. Доступ проверяется при каждом
чтении, изменении и replay: глобально в Privacy, затем подписанным запросом в
Assessment. Проверка требует собственную сессию, формат code/sql, активное
assessment-consent и отсутствие ограничения. В preflight разрешена подготовка,
в in_progress запись только в текущий active этап до deadline. Read purpose позволяет
читать собственные исторические снимки после submission; отмена/отзыв закрывают
доступ к черновику. Внутренний endpoint `/internal/v1/workspace-stage` закрыт
Gateway, использует отдельный контекст подписи, nonce и freshness 30 секунд.
Для локального запуска Workspace задайте HR_PRIVACY_API_URL и
HR_ASSESSMENT_API_URL на доверенные origins работающих сервисов.

`PUT /v1/workspaces/{id}/files` с Idempotency-Key и If-Match сохраняет полный
manifest новой неизменяемой версии; отсутствие файла в новом manifest означает
его удаление из новой версии. Исторические версии сохраняются. При конфликте —
409. Ответ после commit содержит snapshot_id, version, digest и created_at UTC,
подтверждая сохранение. `GET /v1/workspaces/{id}` возвращает последнюю версию,
`GET /v1/workspaces/{id}/snapshots/{snapshot_id}` — исходную. Replay команды
возвращает именно подтверждённую этой командой версию, с новой проверкой доступа.
Допустимы 1–20 текстовых файлов, нормализованные относительные ASCII paths,
до 64 KiB UTF-8 на файл и 256 KiB на snapshot. Файлы хранятся в собственной БД;
Workspace не пишет их в filesystem и не запускает код.

`POST /v1/workspaces/{id}/runs` с Idempotency-Key и snapshot_id возвращает 202,
run_id, исходный snapshot_version и status=pending_runner. Состояние читается
через `GET /v1/workspaces/{id}/runs/{run_id}`. Outbox содержит только UUID refs;
генератор топологии добавляет очередь Code Runner для этих запросов. Обновлённые
broker definitions потребуется применить при следующем запуске стенда; это не
выполнялось сейчас. Runner принимает запросы и возвращает статусы при включённом events profile. Исполнение, runtime
allowlist, лимиты и скрытые тесты впереди; подробности ниже. Черновики
preflight не считаются отправленными работами и не подтверждают категорию.

WorkspaceConsumer удаляет snapshots/runs/workspaces, кеши команд и свои устаревшие
события работы в одной транзакции, оставляет permanent restriction и создаёт ACK
Privacy. Transport подтверждает доставку после commit. Migration 0002_workspace
защищает downgrade заполненных данных и ограничений; Assessment 0004 добавляет
nonce registry. API включён в стандартный Compose, workers — events/all.


## Code Runner: приём запросов и технические статусы (BE-06)

Подписанный `coding-workspace.run_requested.v1` создаёт одну запись запуска в
собственной БД Runner. Повторный event ID и повторный run_id с новым event ID не
создают второй запуск. Изменённые ссылки при том же run_id отвергаются. Данные
снимка запрашиваются у Workspace через `/internal/v1/run-manifest`: отдельные
request/response contexts, Ed25519, freshness 30 секунд, одноразовый nonce,
привязка candidate/workspace/run/snapshot. Проверяются версия, нормализованный
manifest, формат и digest. Files передаются только после проверки актуального
Privacy/Assessment admission. Redirect/proxy отключены, размер ответа ограничен
2 MiB. Файлы/вывод не сохраняются в БД Runner и не передаются в событиях.

`GET /v1/runs/{run_id}` возвращает собственный запуск кандидата: snapshot_id и
snapshot_version, status, error_code, version. При чтении заново проверяются
Privacy и доступ к исходному Workspace snapshot; чужой run_id — 404. API доступен
под `/code-runner/`; HR_WORKSPACE_API_URL задаёт доверенный origin при локальном
запуске. Создание/завершение запусков не являются пользовательскими API командами.

Изолированный исполнитель пока не подключён. Worker `diagnose` переводит
pending_executor в technical_error/executor_unavailable. Отзыв доступа даёт
cancelled/access_withdrawn; недоступность источника оставляет job pending_executor
и откатывает переход. Ни один из этих статусов не является нулевым результатом,
успешным исполнением, оценкой или подтверждением грейда. Пользовательский код
не передаётся host interpreter/subprocess; runtime, sandbox, ресурсы, скрытые
тесты, stdout/stderr и корректные execution results ещё предстоит реализовать.

Signed события run_accepted (version 1) и run_diagnosed (version 2) содержат UUID
refs и обновляют статус запроса в Workspace: pending_executor/runner_diagnosed.
Обратный порядок доставки не регрессирует состояние; повтор POST /runs возвращает
текущий статус. runner_status_path указывает на API Runner с диагностикой, связанной
с исходным снимком. Изменение файлов не перепривязывает запрос к новой версии.

Runner API включён в стандартный Compose, outbox/consumer/diagnostics — events/all.
Новые bindings необходимо применить при возобновлении стендовых проверок; сейчас
Docker/RabbitMQ не запускались и конфигурация брокера не менялась. Migration
0002_runner хранит jobs/restrictions, 0003_attempts — журнал очистки;
0004_results — приватный результат. Workspace 0003 добавляет nonce registry и
проекцию статусов. Downgrade заполненных данных/ограничений запрещён.
Runner deletion consumer удаляет jobs/рабочий outbox, сохраняет tombstone и выдаёт
restricted при незавершённой очистке; deleted только после последней очищенной попытки.
Запоздавший run_requested после удаления не восстанавливает job.

## Экспериментальный адаптер изолированного исполнения (BE-06)

Добавлен отдельный NsjailExecutor для provisioned Linux x86_64 worker: фиксированный
Python 3.12/SQLite demo, namespaces/RO mounts, deny-by-default seccomp, обязательные
cgroups v2 и лимиты времени/памяти/процессов/files/output. Бинарник и состав rootfs
проверяются по pinned SHA-256. Наследование env/FD закрыто, сети и host-interpreter
fallback нет. При неподтверждённой очистке адаптер не выдаёт результат.

Адаптер пока не подключён к сервисному worker, HR_RUNNER_BACKEND по умолчанию
disabled. Runner сохраняет прежнее поведение диагностики. В текущем инкременте
проверены unit-контракты, collector и SQL demo; реальный Linux jail ещё не проверен.
Добавлены durable execution/cleanup ledger, повторная admission-проверка под flock
и recovery: deletion ACK ждёт очистки всех попыток. Режим worker recover включается
явно только с provisioned Linux runtime, стабильным HR_RUNNER_NODE_ID и приватным
scratch 0700; в Compose он не добавлен. Scope pin по путям/device/inode не позволяет
подтвердить очистку заменённого каталога или другого узла. Hidden tests,
включение execution worker после Linux-проверок и оценка остаются впереди.

Rootfs шаблон, настройки provisioning, ограничения и opt-in Linux probes описаны
в [infra/runner/README.md](../infra/runner/README.md). Docker image/rootfs здесь не
собирались и не скачивались; стандартный Compose не получает новых привилегий.


## Приватные результаты Runner

Добавлен GET /code-runner/v1/runs/{run_id}/result: исходный snapshot/version,
UTC completion, статус, exit code/reason и bounded stdout/stderr. Только собственный
кандидат с актуальным доступом к исходному stage; ответы no-store. Combined output
до 64 KiB UTF-8, технические ошибки не раскрывают host/supervisor diagnostics.
Executed означает завершение процесса с exit=0; оценки/pass/hidden test verdict нет.

Внутренний execute_reserved выполняет admission под lock, фиксирует running,
затем после cleanup и повторной admission-проверки атомарно сохраняет result и
UUID-only run_finished event. Workspace получает running/runner_finished без вывода
и не регрессирует при поздних/повторных событиях. После crash recovery подтверждает
cleanup и записывает executor_interrupted, не запускает решение повторно.
Deletion/отзыв доступа отбрасывают вывод, deletion удаляет приватные results.

Исполнение кода закрыто по умолчанию HR_RUNNER_BACKEND=disabled. CLI execute
подготовлен отдельно, в Compose его нет.
Linux/runtime проверки и стендовая integration отложены; новые RabbitMQ bindings
подготовлены, но не применены. Детали: [Runner](../infra/runner/README.md).


## Отмена запуска Runner

POST /code-runner/v1/runs/{run_id}/cancel принимает Idempotency-Key и If-Match.
Владелец может остановить свою pending/running работу даже при недоступном source.
Без незавершённого sandbox Job сразу cancelled; иначе 202/cancel_requested=true
означает ожидание физической очистки. Replay показывает актуальный статус.
После cleanup result пустой, run_cancelled событие проецируется в runner_cancelled.
Отмена не переписывает готовый результат; deletion удаляет replies/results и
сохраняет прежний протокол ожидания cleanup.

Для внутреннего выключенного execution orchestration подготовлена проверка
cancel/tombstone/signed admission с паузой 250 ms между проверками. Медленная/недоступная проверка
останавливает исполнение с техническим статусом; I/O вынесено из watchdog.
Отмена до spawn не запускает процесс, во время выполнения отбрасывает вывод и
требует cgroup cleanup. На настоящем Linux это ещё не проверено; execution CLI по умолчанию выключен, в Compose не добавлен. Подробности: [Runner](../infra/runner/README.md).

Условия и операторские команды: [Runner](../infra/runner/README.md).


## Assessment: серверное прохождение code/SQL demo

Добавлены команды владельца с Idempotency-Key и If-Match версии сессии:

- POST /v1/assessment-sessions/{id}/start — preflight → in_progress, pending этапы.
- POST /v1/assessment-sessions/{id}/stages/{stage_id}/start — только следующий этап,
  server started_at/deadline из закреплённой duration. Повтор не перезапускает timer.
- POST /v1/assessment-sessions/{id}/stages/{stage_id}/submit — workspace_id/snapshot_id;
  после приёма следующий этап либо session submitted.

Первый start даёт version2, start этапа version3, submission version4; дальнейшие
переходы увеличивают session version. SessionView теперь содержит current_stage_id
и progress с deadline, состоянием и immutable artifact refs. Клиент не задаёт порядок,
status, duration, digest или snapshot version. Неподключённые voice/VCV/whiteboard
этапы не стартуют; cancel preflight/in_progress доступен даже после отзыва согласия.

Assessment подтверждает снимок подписанным metadata-only RPC к Workspace. Endpoint
/internal/v1/snapshot-receipt проверяет owner/session/stage/workspace/snapshot и
текущее processing restriction, не возвращает файлы, JWT или рубрики. Nonce/freshness/
purpose-specific signature и фиксированный origin защищают запрос/ответ. Workspace
не вызывает Assessment обратно в этом RPC, избегая рекурсивной admission под lock.
Deadline проверяется до и после RPC; отказ откатывает artifact/command/outbox.
Поздний autosave не перепривязывает отправленную работу к последней версии.

После submission edit/run admission закрыты для завершённого этапа. Собственные
Workspace snapshots и Runner results читаются с отдельным signed read purpose,
который нельзя использовать для исполнения. Worker/intake/monitor используют write
purpose. Все чтения сохраняют свежие processing/assessment consent проверки.

Migration Assessment 0005_assessment хранит progress/refs; Workspace 0004_workspace —
snapshot nonce protection. Readiness/downgrade учитывают таблицы; deletion удаляет
progress, session, cached replies и устаревшие candidate lifecycle events атомарно.
Оба новых RPC остаются закрыты существующими internal Gateway правилами.

Submitted означает приём demo-артефактов. Evaluation, hidden tests, human review
и grade/cooldown теперь реализованы как code/SQL механизмы (см. раздел в конце). Preflight по-прежнему
позволяет готовить черновики, поэтому эта demo-цепочка не заявляется подтверждённой
процедурой квалификации. Просроченный этап не получает автоматический ноль/успех:
запись/submit запрещены, владелец может отменить сессию; timeout resolution впереди.

## Evaluation: приватный приём demo работ

Evaluation принимает подписанное `assessment.stage_submitted.v1` через собственный
consumer. Payload содержит только UUID кандидата, сессии, этапа, Workspace и
неизменяемого snapshot. Проверяются producer, aggregate, версия 3, набор ссылок и
допустимость времени. Один этап создаёт один intake: доставка того же event_id или
нового события с теми же ссылками не дублирует работу; конфликт ссылок отклоняется.
Inbox, intake и `evaluation.intake_created.v1` фиксируются одной транзакцией;
недоступность Privacy повторяет обработку, ограничение обработки не создаёт работу.

`GET /v1/evaluations/stages/{stage_id}` доступен только владельцу с ролью candidate
после свежей проверки Privacy и локального tombstone. Ответ содержит статус
подготовки/проверки, версию, время приёма и `demo: true`. Score появляется только
после полной ручной проверки artifact-критериев; confirmed_grade остаётся null.
В ответе нет исходников, workspace/snapshot refs, скрытых тестов или рубрики.
Это приём работы и подготовка рубрики, а не содержательная оценка. Получение
закреплённой рубрики и исходников описано ниже. Модель, hidden tests и
проверенные тестовые доказательства ещё не подключены. Ручная artifact-проверка
описана в следующем разделе.

Migration `0002_evaluation` создаёт `evaluation_intakes` и `evaluation_subjects`.
Удаление Privacy очищает intake, кеш команд и исходящие intake events, сохраняет
постоянный tombstone и создаёт один ACK в общей транзакции. Позднее событие Assessment
не восстанавливает удалённую работу. Downgrade запрещён при работах или tombstones.

В Compose подготовлены `evaluation-consumer` и `evaluation-outbox` в профилях `events/all`,
API и workers используют собственную signing identity. Генератор topology добавляет
маршрут Assessment → Evaluation; Privacy fan-out и ACK bindings уже общие.
Обновление broker definitions и запуск PostgreSQL/RabbitMQ остаются для отложенного
стендового прогона. Новые ключи не генерировались, контейнеры не запускались.

## Evaluation: закреплённые рубрики и подготовка материала

Внутренний `POST /internal/v1/evaluation-material` Assessment принимает только
подписанный запрос Evaluation с UUID candidate/session/stage/workspace/snapshot.
Отдельные контексты подписи запроса/ответа, nonce с replay protection, свежесть,
точный binding и ограничение ответа 278528 bytes не позволяют использовать запрос
Workspace или старую/чужую квитанцию. Публичный gateway закрывает Assessment internal.

Assessment проверяет собственный tombstone, владельца сессии, submitted stage v3,
ссылки на отправленный snapshot и live assessment consent. Он выдаёт закреплённые
plan/revision/consent IDs, SHA-256 исходного ContentPackage, выбранный Task с рубрикой
и эталоном, относящиеся к нему competencies, версию и digest snapshot из submission.
Этот RPC не передаёт исходники Workspace. Отозванный/отменённый этап и неверные ссылки
дают подписанный отказ без материала; недоступная проверка не выдаёт материал.
Retirement контента закрывает новые сессии, но сохраняет pins уже созданных.
SHA-256 пакета — идентификатор для аудита; Evaluation получает один Task, не весь пакет.

`HR_SERVICE_NAME=evaluation python -m reverse_hr.worker prepare` получает материал
вне локальной DB транзакции, затем повторно проверяет assessment consent в Privacy.
Evaluation получил право только на этот уже существующий signed permission RPC,
без JWT кандидата. Локальный subject lock и повторная проверка версии intake перед
commit защищают от удаления/двойной подготовки во время сетевого запроса.

Успех атомарно сохраняет приватный материал и UUID-only `evaluation.material_ready.v1`.
Статусы: awaiting_material → material_ready; сбой → material_retry с exponential
backoff от завершения запроса, максимум 5 попыток → material_unavailable; отказ →
material_blocked. Отсутствие материала не даёт нулевой оценки. Score и grade всё
ещё null; material_ready означает готовность рубрики и pins, не проверку решения.
GET владельца после подготовки дополнительно проверяет закреплённое assessment
consent и никогда не возвращает эталон, рубрику, исходники или технический traceback.

## Evaluation: получение отправленного исходника и требования к доказательствам

`python -m reverse_hr.worker collect` (HR_SERVICE_NAME=evaluation) берёт material_ready
или artifact_retry intake. Перед чтением исходника он заново получает material из
Assessment и сравнивает все pins с приватно сохранённой рубрикой. Подписанный RPC
Workspace `/internal/v1/evaluation-artifact` имеет отдельный purpose rubric-evidence,
request/response contexts, nonce/freshness/binding и ограничение 2 MiB ответа.
Он требует candidate/session/stage/workspace/snapshot, format, version и digest из
Assessment. FilesCommand валидирует пути/размеры, порядок файлов и SHA-256 manifest
проверяются до принятия. Даже существующий другой snapshot того же Workspace
не выдаётся вместо отправленного.

Workspace подтверждает допуск через отдельный signed `/internal/v1/evaluation-artifact-admission`
Assessment от своей service identity. Assessment проверяет submitted stage v3,
все ссылки, snapshot version/digest/format, отсутствие tombstone/отмены и актуальное
assessment consent. Permit не возвращает рубрику или исходники и не даёт право
исполнять код. Для запроса используется existing material_nonces с отдельными
signature contexts. Workspace вызывает Assessment вне локальной транзакции/lock,
затем под собственным subject lock повторно проверяет ссылки, tombstone, fresh
permit и current Privacy processing. Это исключает обратный порядок блокировок
Workspace → Assessment при Assessment submission → Workspace receipt.

Evaluation после получения source повторяет consent check и под local subject lock
проверяет version/tombstone. В одной транзакции сохраняются private source,
требования каждого критерия рубрики (criterion, competency, max points, evidence
kind, snapshot/digest, pending, points=null) и UUID-only artifact_ready event.
Эти требования ещё не являются доказательствами. Статус artifact_ready не означает
успешного решения; score/grade остаются null, исходники не запускаются и не
передаются модели. Public owner API возвращает только статус, без source/rubric/
requirements. Перед будущим оцениванием доступ нужно проверить заново.

Сбой → artifact_retry с backoff от завершения запроса, максимум 5 попыток →
artifact_unavailable; отказ → artifact_blocked. Исходники/requirements при ошибке
не сохраняются. Concurrent completion не дублирует artifact event. Удаление Privacy
очищает source/requirements вместе с intake и тремя business outbox типами;
отложенный ответ не восстанавливает данные.

Workspace migration 0005 добавляет artifact_nonces, Evaluation 0004 — source,
requirements и retry state; существующие prepared intakes доступны для collect.
Readiness проверяет новые схемы, populated downgrade блокируется до DDL.
Compose profile all получил evaluation-collect с readonly ключами и зависимостями
от Workspace/Assessment/Privacy/Evaluation. Контейнеры и broker не запускались.
Следующий этап — собственно evidence: проверенные тестовые результаты и ручная
проверка критериев с причиной, затем содержательная оценка и политика грейда.

## Evaluation: ручная demo-проверка по доказательствам

Роль assessment_reviewer с MFA уже предусмотрена в Keycloak. Новый приватный
`GET /v1/evaluation-reviews/stages/{stage_id}` возвращает проверяющему закреплённую
рубрику, исходник и последнее решение. Проверка своей работы запрещена. Перед
любым чтением/историей/командой Evaluation заново проверяет материал Assessment,
получает authorized Workspace source и сравнивает его с сохранённым. Сетевые вызовы
выполняются вне Evaluation transaction. Под упорядоченными subject locks actor и
candidate затем проверяются версия, tombstones, текущее ограничение проверяющего
и актуальное согласие кандидата; cached replay тоже проходит эти проверки.

`POST /v1/evaluation-reviews/stages/{stage_id}/reviews` требует Idempotency-Key и
If-Match версии intake. Body: decisions для всех критериев и общая reason; в каждой
decision criterion_key, points (int или null), reason и citations. Citation содержит
нормализованный относительный path, SHA-256 UTF-8 файла, start_line/end_line с
индексацией от 1. Для points, включая 0, нужна хотя бы одна валидная ссылка на строки
файла именно из отправленного snapshot. Проверяются критерии, максимальные баллы,
повторы и реальные границы строк. Отсутствующее доказательство оставляет points=null,
а не автоматически 0; баллы без citations или citations без баллов отклоняются.

Сейчас вручную оцениваются только критерии evidence=artifact. Исходник не может
заменить verified test_result; для такого критерия разрешён только null с объяснением,
пока не подключён проверенный тестовый результат. Если хотя бы один критерий без
баллов — needs_evidence и score=null; иначе reviewed и stage demo score = сумма
по рубрике (0..100). Это не подтверждённый грейд, не результат hidden tests и не
производственный рейтинг. Candidate GET показывает score/status, но не рубрику,
эталон, историю, причины, ссылки или проверяющего; confirmed_grade всегда null.

Каждая команда создаёт новую immutable review revision с проверяющим, причинами,
citations, server timestamp и intake version; исправление оценки требует новой
reason и версии. Текущее состояние requirements связано с последней review revision.
`GET /v1/evaluation-reviews/stages/{id}/history` возвращает максимум 20 записей по
убыванию number; before=<number> читает предыдущую страницу. Replay команды возвращает
актуальное последнее решение, без второго review/event. Решение, score, requirements,
кеш команды и UUID-only evaluation.review_recorded.v1 атомарны. При недостаточном
доказательстве в новой revision предыдущий score снимается, история сохраняется.

Migration Evaluation 0005 создаёт evaluation_reviews и nullable score/review_number
для прежних intakes, readiness и downgrade guard расширены. Deletion кандидата
удаляет reviews, source/material, requirements, business outbox и все stage review
command caches, включая созданные другими actor. ACK failure откатывает purge.
При удалении проверяющего его участие в чужих решениях сохраняется как authorship:
доступ закрыт, его command caches удалены, ACK=data_restricted, полное удаление не
заявляется. Если такие reviews позднее удалены, новый delivery ID того же request
может подтвердить data_deleted. Автоматическая retention-развязка ещё не реализована.

Политика итогового грейда, verified hidden-test evidence, модели/попытки/стоимость,
ручная очередь назначений и production калибровка остаются следующими этапами.
Стендовые проверки PostgreSQL/RabbitMQ/Linux по-прежнему отложены.

Evaluation API теперь входит в базовый Compose запуск и доступен через
`/evaluation/` gateway; internal prefix закрыт. Gateway ждёт его health, так что
Nginx upstream существует в базовой конфигурации. Consumer/outbox включаются
events/all; prepare/collect остаются в all или запускаются отдельной CLI командой.
Изменения конфигурации проверены локально, стенд не запускался.

## Assessment: приватные версии тестовых наборов

Каталог для code/SQL — основа будущей проверки hidden tests. Только
`content_admin` + MFA получает эталоны, ожидаемый вывод, входные файлы и ошибочные
решения. Создание: `POST /v1/content-versions/{revision_id}/tasks/{task_key}/test-suites`;
чтение: `GET /v1/test-suites/{suite_id}`; независимое ревью и отзыв:
`POST /v1/test-suites/{suite_id}/review` и `/retire`. Команды требуют
Idempotency-Key, review/retire также If-Match и непустую reason.

Определение неизменяемо: изменение создаёт новый suite_id/number и новые SHA-256
pins. Связь с опубликованной ContentRevision включает формат, точный текст
эталона и все test_result критерии. Dataset/version выводятся из закреплённого
контента. Набор содержит 1..20 случаев и 2..5 различных ошибочных решений;
runtime — `python-3.12-sqlite-demo-v1`, сравнение — `utf8-exact-v1`.
Входные файлы ограничены каталогом `test_inputs/`, не могут заменить исходник;
проверяются UTF-8 бюджеты, число файлов и пересечения путей.

Жизненный цикл: draft → reviewed → retired; draft также можно отозвать.
Автор не может сам одобрить набор. Review означает только человеческую проверку
спецификации: `runtime_validated=false`, `scoring_enabled=false` всегда.
Реального тестового корпуса и сертификатов исполнения этот этап не создаёт.
Существующие планы/сессии не меняют pins при появлении новой версии набора.

Чистая функция сравнивает stdout/stderr на стороне host без нормализации:
эталон должен пройти все случаи, каждое ошибочное решение — провалить хотя бы
один. Неполная матрица, сбой среды, отмена и лимиты дают inconclusive;
обычный stdout «tests passed» не является доказательством. Функция ничего
не исполняет и не создаёт runtime certificate. Ожидаемый вывод не должен
попадать в guest harness при следующем подключении изолированного исполнения.

Migration Assessment 0007 добавляет test_suites и readiness; populated downgrade
отклоняется до DDL. Авторство создателя, проверяющего и автора отзыва сохраняется
с restricted ACK при удалении, а их доступ и command cache закрываются.
События test_suite_created/reviewed/retired содержат только suite_id/revision_id.
Далее нужны реальная валидация эталона/ошибочных решений в sandbox, привязка
проверенного suite к новой сессии и подписанные test_result evidence для Evaluation.

## Подготовка входов для проверки тестового набора

`reverse_hr.test_harness` строит детерминированный план: reference × cases,
затем каждый mutant × cases (максимум 120 отдельных запусков). Каждый гостевой
manifest содержит только исходник и входные файлы данного случая. Expected
stdout/stderr остаются в SuiteDefinition на host. Проекция копирует файлы,
проверяет reserved paths/коллизии/бюджеты и вычисляет SHA-256; изменять одну
проекцию без изменения других или спецификации можно безопасно.

План фиксирует validation_id, suite/revision UUID, content/definition digest,
runtime fingerprint, формат и comparison policy. Host capture связан также с
source_kind/key, case_key, manifest digest и уникальным attempt_id. Сравнение
пересобирает план из закреплённой спецификации, требует полную матрицу без
повторов и смешения версий/сред/попыток. Нарушение привязки даёт inconclusive.

Это библиотечная подготовка и проверка структуры, без HTTP приёма результатов,
подписанных квитанций или исполнения. Captures в локальных тестах синтетические;
их структура не подтверждает происхождение. Перед включением нужны отдельный
durable suite-validation ledger, admission к reviewed suite, реальная readiness
проверка и подтверждённая очистка каждого sandbox. Обычный Runner job/manifest
не даёт допуска к этому сценарию. Scoring остаётся отключённым.

## Журнал очистки sandbox при проверке тестовых наборов

Runner migration `0007_validation` добавляет отдельные validation_batches и
validation_attempts. Внутренняя библиотека регистрирует точный план под owner lock
и fresh processing check, резервирует следующую попытку с node/scope/UUID до создания
sandbox. Одновременно допускается только одна попытка; следующий case требует
очищенную предыдущую попытку и целостный host capture. Diagnostic mode конфликтует
с execution. CLI worker проверки набора реализован в opt-in режиме `validate`.

Будущий исполнитель должен войти в validation_scope: OS lock, реальная probe
readiness, совпадающие node/runtime fingerprint, fresh trusted-suite admission
для полного плана и повторная проверка owner/tombstone/плана перед active.
Подписанный admission adapter реализован; HTTP-команд запуска нет.
Внутренний execute_reserved вызывает NsjailExecutor только внутри этого scope.

Режим `worker recover` теперь также очищает validation attempts своего node и
cleanup scope. reserved/active → cleaning → cleaned; физическая очистка идёт между
двумя транзакциями. Ошибка или занятый OS lock сохраняют обязанность очистки.
После восстановления batch становится interrupted, потерянный запуск не
повторяется автоматически и не даёт успешного результата. Исходники в плане
удаляются при Privacy deletion сразу, metadata остаётся до очистки всех попыток.
ACK restricted сменяется deleted только после очистки на всех nodes; сбой ACK
откатывает подтверждение, поэтому повтор recovery снова проверяет очистку.

Локальные проверки используют SQLite, настоящие файловые блокировки и временные
каталоги, с явными заглушками readiness/admission. Они не подтверждают работу
Linux namespaces/cgroups или происхождение suite permits. Docker/Linux execution
по-прежнему отложены, scoring остаётся отключённым.

## Подписанный допуск к проверке набора

Assessment обслуживает `POST /internal/v1/suite-validation-admission` только по
подписи Code Runner с purpose=`suite-validation`, свежим временем и одноразовым
nonce. Gateway закрывает весь `/assessment/internal/`. Проверяется автор набора
(поле candidate_id здесь содержит UUID владельца validation batch), его tombstone
и текущее processing permission. Набор должен быть reviewed, связанное задание —
published, а revision/content/definition pins должны совпадать с каталогом.

Assessment проверяет приватную спецификацию и заново строит полный validation plan:
его SHA-256 обязан совпасть с запросом. Квитанция содержит только разрешение и
привязки к owner, batch, suite/revision, hashes, purpose, runtime fingerprint и nonce;
в ней нет эталонов, ошибочных решений, inputs или ожидаемых ответов. Это разрешение
проверить набор, не runtime certificate и не допуск к оцениванию кандидата.
Fingerprint из запроса служит привязкой; Runner отдельно проверяет реальный probe.

`SuiteAdmissionAccess` использует фиксированный Assessment origin, отдельные
Ed25519 contexts, запрет redirect/proxy, timeout и ответ максимум 4096 bytes.
Проверяются подпись Assessment, canonical bytes, свежесть и все привязки.
Signed denial → 409, недоступный/невалидный ответ → 503. Положительные ответы
не кешируются. Validation scope передаёт owner и полный plan в этот adapter;
независимые локальные readiness/processing/cleanup проверки сохраняются.

Runtime OpenAPI обновлён. Новой миграции нет: используется существующий technical
nonce registry Assessment. Внутренний executor/stop monitor, сохранение captures и
opt-in CLI worker реализованы. Проверка полной матрицы, подписанный вердикт, приём
вердикта в Assessment, runtime policy и suite pins сессий реализованы;
далее — purpose-bound проверка отправленного кода кандидатов.

## Исполнение случаев и сохранение host captures

Внутренний `validation_lifecycle.execute_reserved` вызывает существующий
NsjailExecutor под attempt lock, после fresh signed admission и real probe gate.
Каждый case имеет собственные readonly inputs и attempt UUID. StopMonitor повторяет
processing и suite admission вне DB transactions, контролирует свежесть проверок;
отзыв/задержка/сбой доступа останавливают запуск. После возврата executor очистка
проверяется ещё раз, затем повторяются admission/processing/local guards и latched
stop непосредственно перед записью. Потеря разрешения оставляет только redacted
cancelled/technical result; удаление owner не сохраняет новый capture.

Migration `0008_captures` хранит приватные bounded CaseCapture: exact plan/runtime/
source/case/input pins, attempt UUID, Output и completion time. Capture + cleaned
state + terminal UUID-only outbox записываются атомарно. Ошибка commit/outbox
оставляет active obligation; recovery очищает её, прерывает batch и не повторяет
исполнение. Следующий case допускается только после целостной предыдущей capture;
пропущенный/изменённый capture или неочищенная попытка блокируют продолжение.

Executed/runtime_error позволяют собрать остальные случаи. Technical failure,
cancellation и limits дают batch=inconclusive и прекращают очередь. Полная матрица
даёт captures_ready — это ещё не принятие эталона/ошибочных решений и не scoring.
Матрица проверяется по signed trusted expected outputs отдельным finalize;
подписанный вердикт пока не активирует scoring в Assessment. Privacy deletion удаляет captures и terminal events вместе с
private plan; physical cleanup по-прежнему обязательна до deleted ACK.

CLI worker реализован; real probe provisioning и live Linux испытания этого сценария
отложены. Локальные executor outcomes синтетические; production grade/ranking
из них не формируются. Изменённый source требует нового реального probe record.

## Доверенная спецификация и подписанный вердикт набора

Assessment `POST /internal/v1/suite-validation-material` выдаёт полный SuiteDefinition
только подписанному Code Runner, автору reviewed набора и для точного validation plan.
Purpose и Ed25519 contexts отличаются от permission RPC. Текущие status/pins,
processing/tombstone и nonce проверяются заново. Client ограничивает ответ
2 MiB + 4096 bytes, проверяет canonical signature/body, fresh timestamp и все
bindings, digest определения и пересобранный план. Expected outputs остаются на host.

Внутренний `validation_verdict.finalize` принимает только полную матрицу после
подтверждённой очистки всех attempts. Требуются matching node/cleanup scope и
текущий real probe/fingerprint. Trusted material запрашивается вне Runner transaction;
после RPC повторяются readiness/processing/subject/matrix guards. Эталон должен
пройти все cases, каждый mutant — провалить минимум один. Результат accepted/rejected
подписывается собственным ключом Code Runner в отдельном context.

Migration `0009_verdicts` хранит immutable verdict/signature с hashes всего плана
и матрицы, suite/runtime pins, owner, batch и временем. Запись, terminal batch status
и UUID-only verdict event (aggregate version 2) атомарны. Повтор получает свежую
спецификацию/permissions, перепроверяет сохранённую подпись и возвращает тот же
вердикт. Retired content/suite, revoked processing, pending/corrupted captures,
foreign node/scope или недоступность материала не дают положительной квитанции.
Signing/outbox failure оставляет captures_ready для последующей проверки.

Квитанция относится только к demo проверке набора: scoring_enabled=false, без
candidate grade/баллов и без source/expected outputs в proof/event. Assessment
принимает её в приватный журнал, но пока не разрешает оценивать кандидатов.
Opt-in validation worker CLI описан ниже. Privacy deletion очищает proofs/captures/events;
protected downgrade и readiness расширены. Локальные signed receipts настоящие,
Linux outcomes/probe в тестах синтетические; real validation ещё не подтверждена.

## Приём подписанного вердикта в Assessment

`POST /internal/v1/suite-validation-verdict` проверяет отдельные подписи свежего
запроса Code Runner и immutable SuiteVerdict. Проверяются nonce, owner, текущий
reviewed suite/published revision, content/definition pins, время и пересобранный
полный план. Приём повторно проверяет processing под локальным subject lock.
Отозванный доступ или retired suite/content дают подписанный отказ. Повтор того же
batch возвращает квитанцию без второго события; конфликтующий proof получает 409.

Migration Assessment `0008_verdicts` хранит приватные proof/signature и время приёма.
Запись, UUID-only outbox и transport nonce атомарны; сбой подписания/сохранения
откатывает транзакцию. Приватный GET `/v1/test-suites/{suite_id}/validations/{validation_id}`
доступен content_admin с MFA и свежим processing автора и читателя. Он перепроверяет
структуру, подпись и owner/suite/batch bindings. Deletion автора удаляет журнал
и его business events; сохранённое авторство контента по-прежнему требует restricted ACK.

Квитанция подтверждает подпись и привязки: `runtime_validated=false` и
`scoring_enabled=false`. Она не проверяет реальную матрицу captures или provenance
runtime. Runtime policy, attestation и validation очередь/worker описаны ниже;
suite pins сессий описаны ниже. Docker/PG/RabbitMQ/Linux проверки отложены.

## Политика допуска runtime и свидетельство Runner

`HR_ASSESSMENT_TRUSTED_RUNTIMES` — JSON allowlist оператора, по умолчанию `[]`.
В Compose передаётся из `ASSESSMENT_TRUSTED_RUNTIMES`. Каждая запись содержит
`policy_id`, `node_id`, SHA-256 `fingerprint`, timezone-aware `approved_at` и
`expires_at`. Максимум 32 записи, уникальные policy IDs и пары node/fingerprint;
срок одной записи до семи дней. Изменение требует применения конфигурации Assessment.
В репозитории нет одобренных runtime или настоящих probe records.

Внутренний `validation_attestation.attest` проверяет сохранённый подписанный вердикт,
полный cleaned capture snapshot и node/cleanup scope; свежие processing, signed
suite admission и реальный local readiness gate повторяются. Свидетельство в отдельном
Ed25519 context связывает digest вердикта, owner/batch и ProbeRecord с node/fingerprint,
12 passed probes и временем проверки. Probe обязан предшествовать завершению
вердикта и быть не старше 24 часов; проверка после исполнения не заменяет его.

Verdict delivery принимает optional attestation/signature, проверяет отдельную
подпись и binding, возвращает подписанный digest свидетельства. Migration Assessment
`0009_runtime` хранит private report/signature. Поздняя доставка добавляет свидетельство
один раз атомарно с UUID-only event; повтор с новым issued_at и той же probe identity
не заменяет сохранённый report, другой node/probe закрыт. Deletion очищает данные/events.

Приватный GET `/v1/test-suites/{suite_id}/validations/{validation_id}/runtime-admission`
для content_admin/MFA заново проверяет signatures/processing/current catalogue и
политику. `runtime_admitted=true` требует accepted verdict, активный набор и контент,
свидетельство с probe не старше 24 часов и соответствующую действующую allowlist entry,
одобренную до probe. Истечение/удаление policy, retirement или отзыв доступа закрывают
допуск без кеша. Это доверие к утверждению подписанного Runner и конфигурации оператора;
независимую сертификацию изоляции оно не выполняет. Suite/receipt всё ещё имеют
`runtime_validated=false`; scoring и candidate grade не активируются этим endpoint.

## Управляемая очередь валидации наборов

Runner migration `0010_queue` хранит private `validation_work`: batch/owner/node/scope,
status, retry count/deadline, bounded error code, immutable attestation/signature и
проверенную квитанцию Assessment. Постановка атомарна с новым ValidationBatch;
existing batch требует exact plan/owner и собственные node/scope всех attempts.
План из локального JSON перепроверяется по signed material из Assessment и текущему
реальному runtime fingerprint. Idempotency — validation UUID; смена плана/узла запрещена.

После миграций на отдельно подготовленном Linux узле с собственными ключами,
HR_SERVICE_NAME=code-runner, HR_RUNNER_NODE_ID, HR_RUNNER_EXECUTION_ENABLED=true,
настройками Nsjail/cgroups/rootfs и свежим probe record можно выполнить:

```sh
python -m reverse_hr.validation_queue --owner-id "$SUITE_OWNER_ID" --plan-file /private/path/plan.json
python -m reverse_hr.worker validate
```

`plan.json` — результат `test_harness.build_plan` для reviewed каталога и текущего
runtime fingerprint; CLI ограничивает вход 32 MiB. Команда не принимает ожидаемые
результаты как источник истины. План и скрытые тесты остаются приватными.
Режим execution сериализуется с diagnostic mode, в Compose worker автоматически
не запускается. Default execution gate остаётся выключенным.

Worker держит стабильный batch OS fence и обрабатывает один шаг за tick: recovery
своей попытки, следующий case, full-matrix finalize, attestation или signed delivery.
Fresh processing/admission/readiness и существующие capture/cleanup guards действуют
на каждом шаге. Pending output после crash не воспроизводится: cleanup-only recovery
делает batch interrupted, требуется новый validation UUID. Technical/limit/cancelled
дают inconclusive без вердикта и candidate score. Accepted и rejected verdicts
доставляются как metadata; `done` подтверждает приём Assessment, не scoring/admission.

Attestation сохраняется перед RPC доставки. Потеря ответа или local ACK/outbox failure
повторяет тот же proof/report, а не исполнение случаев. Receipt bindings проверяются,
final owner lock/processing и exact stored material повторяются перед done + UUID-only
delivery_confirmed event aggregate v3. Между зависимыми сбоями применяется backoff
5/10/20/40 секунд; после пяти failures — needs_attention. После устранения причины
оператор может повторить enqueue с `--retry`: нужны свежие signed material/readiness;
interrupted/inconclusive batches этим способом не возобновляются.

Privacy deletion немедленно удаляет queue/report/receipt и business events. Незавершённые
attempts остаются cleanup obligations; worker на собственном node/scope обрабатывает
их даже без queue material и свежего probe. Deleted ACK только после физической очистки.
Миграция защищает все старые populated runner tables/tombstones до первого DDL.
Локальные tests используют настоящие signatures/SQLite/OS locks, synthetic execution/probe;
реальный Linux runtime и PostgreSQL concurrency ещё не подтверждены.

## Приватные привязки тестовых наборов в планах и сессиях

`POST /v1/assessment-plans` принимает optional `test_suite_selections`: список
`revision_id`, `task_key`, `suite_id`, `validation_id`. Непустой список обязан
покрывать ровно все code/SQL задания с `test_result` в плане. Content_admin/MFA
выбирает reviewed набор с accepted подписанным вердиктом и attestation; текущая
операторская runtime policy, published content и processing автора проверяются.
Пустой список сохраняет legacy demo/manual режим с неподтверждёнными test_result.

Migration Assessment `0010_pins` хранит private `test_pins` + SHA-256 на PlanVersion
и PracticalSession. Pin включает позицию/task/revision, SuitePin с content/definition/
runtime digests, validation UUID, hashes вердикта и attestation, node и policy UUID.
Новая сессия получает глубокую JSON копию со своим stage UUID. Plan и session pins
перепроверяются структурно/по hash; очищенный или повреждённый pin не превращается
молча в legacy режим. Старые nullable поля означают отсутствие pins, без автоматического
подбора «последнего набора». Обновление каталога не переписывает существующую сессию.

Публикация плана/replay и новая сессия требуют fresh exact runtime admission.
Withdrawal/expiry/смена policy UUID или retirement запрещают новые сессии;
list plans скрывает такие pinned планы. Повтор ранее созданной сессии возвращает
её историческое состояние, но не выдаёт разрешение на исполнение. Owners блокируются
в стабильном порядке; suite locks берутся до отсортированных content revision locks.
Plan/session/outbox/idempotency атомарны; protected downgrade/readiness обновлены.

Candidate PlanView/SessionView не включают private pins, fingerprints, policy,
verdict metadata, hidden fixtures или expected outputs. Signed Evaluation material
содержит optional metadata-only `test_suite` для своего stage, привязанную к task/
revision/content hash. Server повторно проверяет stored proof/report signatures,
digests, stage fields и processing источника. Client отклоняет чужую revision/task/
content/stage. Полные test cases/expected outputs этим полем не передаются.

Исторический экспорт Evaluation сохраняет исходные pins после retirement/expiry;
он не является runtime permission. Исчезнувший proof, revoked source processing
или corrupted pins закрывают экспорт без нулевой оценки. Удаление кандидата удаляет
session pins вместе с сессией; retained авторство plan/content по-прежнему требует
restricted ACK. Suite/receipt runtime_validated=false: сам по себе suite pin не присваивает grade.
Purpose-bound submitted execution и grade policy описаны в следующем разделе.

тестов и **механизм** итогового решения для code/SQL. Реального калибровочного корпуса,

### Отправленный снимок и скрытые тесты

`POST /internal/v1/submitted-tests` выдаёт Code Runner отдельный подписанный допуск
и private suite material для конкретных candidate/session/stage/workspace/snapshot,
node и runtime fingerprint. Проверяются завершённая отправка, consent, processing
кандидата и авторов, private pins и текущая runtime policy. Отдельный
`POST /internal/v1/submitted-tests-source` выдаёт неизменяемый Workspace manifest,
проверяя точные snapshot version/digest и suite binding через Assessment.
Обычный Workspace write/run permit после отправки по-прежнему закрыт.

Signed `assessment.stage_submitted.v1` также создаёт Runner SubmittedJob.
Opt-in `python -m reverse_hr.worker grade-tests` требует тех же provisioned nsjail,
стабильного node ID, свежего real probe и execution mode, что и существующий worker.
Он выполняет по одному скрытому случаю, добавляя в guest только исходники и fixtures;
expected outputs и reference/mutants не передаются исполняемому коду кандидата.
До создания процесса коммитится SubmittedAttempt. OS stage/attempt locks защищают
от параллельного исполнения. Вывод становится доказательством только после cleanup,
повторной проверки допуска/runtime и сопоставления на host. Восстановление очищает
процесс и отмечает interrupted; потерянный вывод повторным исполнением не заменяется.
Пять dependency failures с backoff заканчиваются needs_attention. Внутренняя
`submitted_runner.retry_job` возобновляет только dependency jobs с подтверждённой
очисткой; interrupted work требует новой кандидатской попытки.

`POST /internal/v1/submitted-test-result` в Evaluation проверяет две подписи:
свежий transport request и неизменяемый Runner TestProof. Proof включает snapshot,
SessionSuitePin, исходный ProbeRecord, полный список case outcomes, attempt IDs,
input/capture/case hashes; stdout и ожидаемые ответы в него не включаются.
Evaluation сверяет весь список case keys/criterion keys/hashes с private metadata
Assessment; неполный набор даже с действующей подписью не даёт баллы. Natural replay
не заменяет proof и не повторяет исполнение. Для `test_result` применяется доля
passed cases в пределах баллов критерия; inconclusive оставляет баллы unset.

Reviewer workspace содержит `trusted_test_points` и `test_proof_digest`.
Ручная stage review с `test_proof_digest` может принять только вычисленные баллы;
цитата исходника не заменяет test proof. Artifact-критерии по-прежнему требуют
проверенных file hashes и line ranges. `POST /internal/v1/stage-score` экспортирует
Assessment свежий signed набор criterion points и immutable review references.

### Калибровка, итог и повторные попытки

Content_admin/MFA создаёт `/v1/grade-policies` для конкретного PlanVersion:
weights по всем компетенциям (сумма 100), обязательные minimums, pass_score,
retry_seconds и отдельный grade_change_seconds (по умолчанию 90 дней).
Политика первоначально draft. Другой content_admin/MFA утверждает её через
`/v1/grade-policies/{policy_id}/approve`, предоставляя CalibrationData: hash источника,
held-out cases, нормализованные scores и согласованные независимые expert labels.
Проверяются уникальность случаев/экспертов, coverage, минимум 20 validation cases,
не менее пяти примеров каждого класса и заданная точность по каждому классу.
Эти ограничения — технические проверки входных данных, а не научное обоснование
достаточного размера выборки. Утверждающий эксперт отвечает за происхождение и
разделение корпуса; синтетические тестовые fixtures не публикуются в рабочие policies.
GET policy возвращает данные для проверки; retire с CAS/причиной закрывает применение.

SessionCommand принимает optional `grade_policy_id`. Новая scored сессия закрепляет
hash утверждённой policy и её calibration; legacy сессии остаются без грейда.
Смена policy не обходит уже назначенные cooldown. Новая попытка того же уровня
также запрещена, пока предыдущая scored сессия ожидает решения.

`GET /v1/assessment-sessions/{session_id}/evaluation` показывает кандидату текущий
итог. `/v1/assessment-grade-reviews/{session_id}` доступен независимому
assessment_reviewer/MFA. Сумма points/max_points нормализуется по компетенциям,
затем применяется закреплённая версия weights/thresholds. Пока есть missing evidence,
итог nullable. Предложение grade само не меняет подтверждённый уровень.

`POST /v1/assessment-grade-reviews/{session_id}/decisions` принимает confirm/reject/
technical_failure и содержательную причину. Confirm требует совпадающего свежего
`evidence_digest`, полного набора human stage reviews и прохождения minimums/thresholds.
Человек может изменить оценки посредством новой stage review или отклонить итог с
причиной. Decision завершает сессию (`completed`), сохраняет историю доказательств,
отдельные retry/grade-change deadlines и UUID-only событие. Неудача не понижает уже
подтверждённый grade; technical_failure не выставляет ноль и не назначает retry cooldown.
Общий grade хранится в Assessment и проецируется в Candidate через подписанное
событие и отдельный signed RPC. Matching использует этот подтверждённый грейд
через отдельный разрешённый экспорт Candidate, описанный ниже. Media/VCV/whiteboard evidence этим code/SQL этапом не реализуется.

### Будущая LLM-оценка

`evaluation_llm.ModelGateway` — интерфейс провайдера с structured ModelReply.
Модель возвращает предложение ReviewCommand и token/cost metadata, а не test certificate
или подтверждённый grade. Prompt version/hash, exact material/source hash, модель,
длительность, usage/cost и статус хранятся в ModelAttempt. Добавлен настраиваемый Chat Completions gateway;
`HR_EVALUATION_LLM_ENABLED=false` по умолчанию. Реальные модель/ключ/тарифы пока не настроены.

MFA reviewer может запросить `/v1/evaluation-reviews/stages/{stage_id}/model-attempts`.
Injected gateway обрабатывается `evaluation_llm.run_one`; один bounded thread и timeout
до 30 секунд ограничивают зависший вызов. Не более трёх отдельных попыток на stage;
technical_failure оставляет output/score unset. Endpoint interrupt отбрасывает late reply
и позволяет создать следующий UUID. После предложения человек явно ссылается на
`model_attempt_id` в stage review, принимает/меняет баллы и приводит проверяемые цитаты.
Наличие LLM proposal не заменяет hidden tests, независимую stage review или grade review.
Grade policy может требовать `required_llm_model` и `required_llm_prompt_digest`:
без принятого human reviewer предложения ровно этой модели/промпта итог остаётся unset.
Signed stage-score export перепроверяет ModelAttempt и exact input hash.
LLM attempts/output, signed test evidence, grades/decision caches удаляются вместе с
данными кандидата; неочищенные Runner attempts задерживают deleted ACK. Авторство
policy/calibration/review остаётся restricted и не разрешает новые операции.

Новые migrations: Runner `0011_submitted`, Assessment `0011_grades`, Evaluation
`0006_tests`/`0007_models`. Они защищают данные до любого downgrade DDL; readiness
проверяет новые таблицы. Контракты OpenAPI обновлены. Docker/PG/RabbitMQ/Linux и
реальная LLM-инференс/пилотная калибровка не проверялись.


### Подтверждённый грейд в Candidate

Candidate consumer обрабатывает `assessment.grade_decision_recorded.v1`. Событие
содержит только UUID; детали получаются через подписанный
`POST /internal/v1/confirmed-grade` Assessment с отдельным purpose/context,
свежим nonce и точным связыванием candidate/session/decision/reviewer/session version.
Проверяются текущие ограничения кандидата и авторов, а также assessment consent.
В ответе только специализация, целевой грейд, статус решения, дата и `demo=true`;
исходники, баллы, причины, калибровка и скрытые тесты не передаются.

`GET /v1/candidates/me` возвращает подтверждённый грейд для текущей специализации.
Самостоятельно указанный `declared_grade` не меняет подтверждённый уровень.
`GET /v1/candidates/me/grade-history` доступен только самому кандидату и показывает
минимальную историю подтверждений, отказов и технических сбоев по специализациям.
Профиль можно создать после решения: сохранённая история используется при чтении.
Повторные event UUID и повторная доставка decision UUID не создают новую запись;
конфликтующее решение отклоняется. Запоздавшее событие не понижает грейд: Assessment
сейчас разрешает только повышение. Новые правила понижения/отзыва потребуют отдельного
версионированного контракта. Изменение видимого подтверждённого грейда увеличивает
версию профиля для защиты от устаревшего `If-Match`.

Privacy удаляет историю вместе с профилем и command caches. Постоянный tombstone
блокирует восстановление истории поздним событием. Migration Candidate `0004_candidate`
и readiness включают таблицу истории; downgrade проверяет данные до DDL. Доставка
в RabbitMQ требует обновлённой topology из `scripts/configure_events.py`; существующие
сервисы и брокер автоматически не перезапускались. Подключение Matching описано
ниже; реальная LLM-инференс остаётся непроверенной.


### Настройка LLM worker

Опциональный `python -m reverse_hr.worker evaluate` работает только в Evaluation.
Адаптер использует один `POST /v1/chat/completions`, строгую JSON schema,
`max_completion_tokens`, `store=false`, без tools, streaming, fallback и HTTP retry.
Формат сверён с [официальным API](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create).
Поддержка этих параметров и точное возвращаемое имя модели должны быть проверены
для выбранного провайдера; неподдерживаемый или усечённый ответ закрывает попытку.

Настройки в `.env.example`: `EVALUATION_LLM_ENABLED`, `EVALUATION_LLM_MODEL`,
`EVALUATION_LLM_CONFIG`, `EVALUATION_LLM_TIMEOUT_SECONDS`. Config — JSON с fixed HTTPS
origin, max_request_bytes, max_input_tokens, max_output_tokens,
input_microusd_per_million_tokens, output_microusd_per_million_tokens,
stage_budget_microusd. Тарифы задаёт оператор: в коде нет выбранной модели или
предполагаемой актуальной цены. Config резервирует верхнюю оценку для всех трёх попыток.
Каждая новая попытка в одном stage требует той же модели/config, даже после сбоя.
Input guard ограничивает байты запроса с запасом; он не заменяет tokenizer провайдера.
Стоимость в ledger — оценка по usage и заданным ставкам, не счёт; неизвестный usage
после timeout остаётся null, но попытка и её резерв не освобождаются. Строгий денежный
лимит на стороне провайдера остаётся отдельной настройкой аккаунта.

Ключ читается из `HR_EVALUATION_LLM_KEY_FILE`, максимум 4096 байт. В Compose это
`.secrets/llm-api-key`, смонтированный только в `evaluation-llm`. Не помещайте ключ в
JSON config: публичная конфигурация сохраняется в ledger и видна MFA reviewer.
Необходимо явно включить профиль `llm`; только worker имеет сеть `llm-egress`.
Evaluation API остаётся в internal backend network. Конфигурация инфраструктуры
подготовлена, действующие контейнеры и `.env` не изменены.

Pending попытки с несовместимой моделью/config/prompt или отказом source admission
закрываются как blocked до внешнего вызова. Принятая работа фиксируется как running
перед запросом. После падения процесса running не отправляется заново: reviewer
может interrupt и запросить следующий UUID в пределах трёх попыток. Late reply
после interrupt не сохраняется. Модель не выставляет score/grade сама; проверка
цитат и явное human review остаются обязательными.

Провайдер получает task/rubric и files с SHA, без candidate/session UUID, consent,
private suite pins и case metadata. HTTP transport отключает ambient proxies/redirects,
ограничивает request/response и timeout. Ошибки провайдера не попадают в outbox,
пользовательские ответы или worker logs. Реальная внешняя инференс в этой реализации
не запускалась; локальные проверки используют synthetic HTTPS response doubles.


### Matching и базовый Hiring

Candidate предоставляет подписанный `POST /internal/v1/market/profile` только
Matching/Hiring. Ed25519 связывает владельца, вызывающий сервис, purpose, все ссылки,
nonce и свежесть запроса/ответа. Проверяются текущие ограничения обработки и согласие
`profile_publication` версии `demo-v1`. Экспорт содержит имя, специализацию,
подтверждённый грейд, ссылку на решение, версию профиля и заявленные навыки;
контакты, самостоятельно заявленный грейд и оценочные доказательства в индекс не попадают.

Кандидат управляет публикацией через `PUT /v1/candidates/me/publication`
(`published`, `consent_id`, `declared_skills`, Idempotency-Key и If-Match профиля).
Отключение требует `consent_id=null`. `PUT /v1/candidates/me/contacts` сохраняет
в Candidate вручную заданные email/phone; эти значения не считаются проверенными OIDC.
Изменение публикации или видимого подтверждённого грейда атомарно создаёт
UUID-only событие. Matching consumer обновляет проекцию по свежему экспорту,
защищает её inbox и watermark от повторных/запоздавших событий; отзыв согласия
очищает карточку. Повторное подтверждение того же грейда сохраняет первую ссылку
на доказательство в карточке.

Hiring владеет критериями найма: `POST /v1/hiring-needs`,
`PUT /v1/hiring-needs/{id}` и `GET /v1/hiring-needs?organization_id=...`.
Это критерии специализации, минимального подтверждённого грейда и обязательных
заявленных навыков со статусами draft/published/closed. Полная доска вакансий
и модерация публикаций этим API не реализованы. Доступ требует актуального членства
owner/recruiter в проверенной организации через подписанный экспорт Employer.

`POST /v1/matches` принимает organization_id, need_id, mode (production/demo)
и необязательный UUID cursor after. Совпадение требует одинаковой специализации,
грейда не ниже минимального и всех required_skills среди declared_skills.
Версия правила `confirmed-grade-declared-skills-v1`: score равен 100 минус 10
за каждую ступень превышения требуемого грейда, равные scores сортируются по UUID.
Это воспроизводимое правило, не измеренная точность подбора; навыки не проверены
оценкой. Страница ограничена 200 карточками, ранжирование выполняется внутри страницы.
Все текущие подтверждения помечены demo=true: production возвращает пустой подбор,
для технической проверки необходимо явно выбрать demo.

Сохраняются snapshot запроса, digest критериев и версия ранжирования.
`GET /v1/matches/{id}` доступен только автору запроса. Перед любым ответом,
включая повтор команды, Matching заново проверяет критерии и разрешённые профили.
Изменение критериев даёт конфликт; изменённые/скрытые карточки исключаются.
Недоступный источник не разрешает выдачу сохранённых персональных данных.

Hiring: `POST /v1/invitations`, `GET /v1/invitations`, `GET /v1/invitations/{id}`,
`POST /v1/invitations/{id}/accept`, `/decline`, `/revoke`.
Приглашение независимо от вакансии; обязательны компания, описание, контакт
работодателя и диапазон месячной зарплаты в RUB. Статусы sent/accepted/declined/
revoked/expired; изменения требуют Idempotency-Key и текущего If-Match.
Кандидат принимает или отклоняет собственное приглашение; работодатель отзывает
отправленное. Истечение проверяется при чтении/действии, отдельного expiry worker нет.

Принятие требует конкретного действующего contact_disclosure consent и атомарно
публикует signed UUID-only событие. Privacy асинхронно создаёт разрешение компании.
До доставки события `GET /v1/invitations/{id}/contacts` закрыт. После доставки Hiring
получает контакты из Candidate через подписанный RPC с новой проверкой членства,
ограничений и разрешения для точного приглашения. Контакты не хранятся и не кешируются
в Hiring. Отзыв согласия/разрешения закрывает доступ; повтор принятого события
не восстанавливает отозванный grant.

Privacy deletion очищает Candidate publication/contacts, Matching projection и
снимки с участием субъекта, а также Hiring needs/invitations, созданные субъектом,
и приглашения этому кандидату. Inbox, очистка, постоянный tombstone и deleted ACK
фиксируются атомарно; позднее событие не восстанавливает профиль.
Текущая политика удаляет созданные сотрудником записи; перенос корпоративных записей
и политика их хранения требуют отдельного решения. Глобальное завершение удаления
по всем 17 сервисам этим инкрементом не заявляется.

Миграции: Candidate 0005_candidate, Employer 0006_employer, Matching 0002_matching,
Hiring 0002_hiring. Readiness проверяет новые таблицы; downgrade с данными запрещён.
Matching/Hiring API подключены к Gateway; внутренние RPC закрыты на Gateway.
Перед запуском доставки нужны обновлённая topology из scripts/configure_events.py,
миграции и Matching/Hiring workers профиля all. Конфигурация .env/.secrets и запущенные
контейнеры этим инкрементом не менялись.

Проверка: 810 passed, 52 skipped, Ruff lint/format и OpenAPI comparison проходят.
Интеграционные тесты используют отдельные SQLite БД сервисов, настоящий Ed25519,
API и транспорт с управляемой доставкой. Live PostgreSQL/RabbitMQ/Compose и гонки
под PostgreSQL остаются отложенными. Диалоги и уведомления описаны далее; задания
компаний и расписания реализованы далее; ATS остаётся следующей частью найма.


### Диалоги Hiring и уведомления внутри платформы

Принятие приглашения создаёт ровно один диалог в той же транзакции. Dialog ID
совпадает с invitation ID; повтор принятия не создаёт дополнительные диалоги.
Migration Hiring `0003_hiring` создаёт диалоги для уже принятых приглашений;
исторические сообщения/уведомления не выдумываются.

`GET /v1/dialogs/{id}` возвращает только ссылки, версию, последний номер сообщения
и признак блокировки. `GET /v1/dialogs/{id}/messages?after=0` читает до 50 сообщений
по возрастающему номеру; `POST /v1/dialogs/{id}/messages` принимает plain text
до 4000 символов, Idempotency-Key и If-Match диалога. Отправка увеличивает номер
сообщения и версию диалога. Кандидат читает/пишет в своём диалоге; работодатель —
только с актуальным owner/recruiter членством в проверенной организации.

Для чтения и отправки текста требуется действующее разрешение Privacy на точное
принятое приглашение. До доставки accepted события в Privacy текст закрыт.
Отзыв согласия или grant закрывает сообщения и повтор команды отправки;
недоступность Privacy/Employer не разрешает выдачу сохранённого текста.
В command cache хранится только message ID, текст остаётся в Hiring.
Произвольный текст не переносится в уведомления, логи или event payload.

Кандидат вызывает `POST /v1/dialogs/{id}/block` с текущим If-Match и Idempotency-Key.
Блокируется организация для этого кандидата: отправка/чтение сообщений, выдача
контактов и новые приглашения закрываются во всех её диалогах с кандидатом.
Блокировка не требует действующего contact grant; работодатель не может снять её.
Разблокировка этим API не поддерживается. Само Privacy разрешение не переписывается;
Hiring дополнительно проверяет локальную блокировку при выдаче контактов.

`POST /v1/dialogs/{id}/complaints` принимает приватную причину (до 2000 символов)
и необязательный message_id ровно из этого диалога. Жалоба доступна участнику
и после блокировки/отзыва contact grant; повтор не создаёт дубль. Причина остаётся
в Hiring, в outbox только UUID references. Очередь модератора и решения описаны далее;
SLA рассмотрения и апелляции остаются отдельным этапом.

Hiring атомарно создаёт минимальную notice reference и событие
`hiring.notification_requested.v1` при отправке/принятии/отклонении/отзыве приглашения
и отправке сообщения. Уведомление о приглашении идёт кандидату, о принятии/отказе —
автору приглашения; о сообщении кандидата — автору приглашения, о сообщении сотрудника —
кандидату. Общая рассылка всем сотрудникам компании не производится.

Notification получает детали по fresh signed `POST /internal/v1/market/notice`
Hiring: nonce, purpose, caller whitelist, точный recipient/notice binding.
Consumer защищён inbox и натуральным notice ID; разные event ID одного notice
не создают дубли. Уведомления содержат только вид события и invitation ID;
в них нет текстов сообщений, зарплаты, описания компании, email/телефона или файлов.
Ограничения Privacy, блокировка компании и текущий доступ получателя проверяются
заново при чтении/отметке прочитанного; сохранённые positive permissions не используются.

`GET /v1/notifications?after=...` показывает до 50 собственных записей с UUID cursor.
`POST /v1/notifications/{id}/read` требует Idempotency-Key и If-Match уведомления.
`GET/PUT /v1/notifications/preferences` управляет единственным реализованным каналом
in_app (по умолчанию включён, начальная версия 1). PUT требует Idempotency-Key
и If-Match. Отключение скрывает inbox, но сохраняет записи и статус прочтения;
повторное включение показывает доступные записи. Email/SMS/push и рекламные рассылки
не подключены; предпочтение in_app не является согласием на рекламу.

Privacy erasure удаляет сообщения, жалобы, диалоги, блокировки, notice references
и связанные command caches в Hiring. Notification очищает данные/предпочтения
субъекта и уведомления, где он кандидат, автор сообщения или автор приглашения,
включая ответы/отметки прочтения другой стороны. Постоянные tombstones и атомарные
ACK не допускают позднего восстановления даже при доставке удаления в Notification
раньше Hiring. При удалении сотрудника очищаются также жалобы со ссылкой на его
сообщения, даже если сам диалог сохраняется.

Добавлены Notification migration `0002_notification`, readiness, consumer/publisher,
топология и Gateway. Notification API включён в основной Compose; его event workers
используют профиль all. Для доставки нужны новые migrations, topology и workers;
.env/.secrets и работающие контейнеры автоматически не обновлялись.
Проверки используют отдельные SQLite БД, настоящий Ed25519 и управляемую доставку
событий между API. Live PostgreSQL/RabbitMQ/Compose остаются отложенными.

Финальная проверка этого инкремента: **830 passed, 52 skipped** (20 новых cases),
Ruff lint/format (195 Python files), runtime OpenAPI comparison и git diff --check
проходят. Структура Compose проверена без запуска Docker. Проверены повторы и
версии сообщений, grant/membership revocation, блокировка, приватность жалоб,
signed notice export/transport, предпочтения/read, миграции и очистка производных данных.


### Рассмотрение жалоб Hiring

`GET /v1/hiring-complaints?status=open&after=...` возвращает очередь до 50 записей
без текста жалобы/сообщений. `GET /v1/hiring-complaints/{id}` возвращает причину,
только конкретное сообщение, указанное в жалобе, и историю решений; весь диалог,
контакты и описание приглашения не выдаются. Обязательны company_moderator и MFA.
Подписанный Employer affiliation export проверяет любое действующее членство,
включая technical_expert и компании с отклонённой верификацией: сотрудники компании,
автор приглашения, жалобы или целевого сообщения не рассматривают собственное дело.
Недоступность Employer/Privacy закрывает чтение и решение.

`POST /v1/hiring-complaints/{id}/decisions` принимает outcome=upheld/dismissed
и содержательную reason; нужны Idempotency-Key и текущий If-Match дела.
Дело open переходит в терминальный статус; решение сохраняет проверяющего,
время, причину и версию. Повтор команды не создаёт запись, сменить окончательное
решение повторным POST нельзя. В outbox только UUID, в command cache только ID дела.
Сохраняется ручное решение человека; автоматическая санкция компании не назначается.
`GET /v1/dialogs/{dialog}/complaints/{id}` показывает автору жалобы её статус,
версию и время без закрытых материалов модерации. Независимая кандидатская блокировка
компании продолжает действовать отдельно от исхода жалобы.

Hiring migration `0004_hiring` создаёт дела open для старых жалоб, без выдуманных
решений, и защищает данные от downgrade. Privacy erasure очищает дела, решения,
их caches/outbox вместе со связанной жалобой; при удалении модератора очищаются
рассмотренные им жалобы. Tombstones и общий порядок subject fences закрывают
последующее чтение/команды. Апелляции, санкции и технические SLA/таймеры впереди.

### Предложения компаний: все форматы контента

Assessment предоставляет `POST /v1/company-task-proposals` с organization_id,
name и ContentPackage. Поддержаны **code, sql, vcv, voice, whiteboard**, в том числе
смешанные пакеты. Проверяются уникальность компетенций/задач/критериев, соответствие
доказательств формату, сумма 100 баллов на рубрику, размер пакета и общая длительность
до двух часов. Это структурная проверка, не сертификат скрытых тестов или калибровка.
Конструктор не исполняет код, не запускает запись видео/голоса или среду доски.

Доступ требует employer role и fresh signed Employer content-membership:
owner/recruiter/technical_expert проверенной организации. Обычное membership
Matching/Hiring по-прежнему разрешает только owner/recruiter. Source dataset/version
предложения задаёт сервер через company/proposal UUID; все пакеты остаются demo=true.
Reference answers и рубрики доступны только уполномоченным сотрудникам и независимому
content_admin с MFA после отправки, в Candidate/Matching они не переносятся.

`PUT /v1/company-task-proposals/{id}` изменяет только собственный draft автора
с текущими Idempotency-Key и If-Match; организация неизменна. Другие уполномоченные
сотрудники могут отправить вариант через `POST .../{id}/submit`, но не переписать
чужое авторство. После submit контент и digest зафиксированы.
`GET /v1/company-task-proposals?organization_id=...&status=...&after=...` даёт
ограниченный список компании без содержимого; content_admin без organization_id
получает очередь submitted. `GET .../{id}` получает полный допущенный вариант.

`POST .../{id}/review` требует content_admin, MFA, точный digest, If-Match,
Idempotency-Key и содержательную причину. Автор и любой действующий сотрудник
компании исключены из независимого рассмотрения. Approve атомарно создаёт одну
опубликованную immutable ContentRevision в существующем demo-банке с авторством,
проверяющим и причиной; reject не создаёт версии банка. Повтор не дублирует публикацию.
Статусы предложения draft/submitted/approved/rejected/withdrawn.

`POST .../{id}/withdraw` с причиной и текущей версией отзывает предложение;
у approved также переводит его опубликованную версию банка в retired. Снимки
ранее созданных оценочных сессий не переписываются. Ответы команд сохраняют только
proposal ID и заново проверяют доступ; source unavailable не выдаёт старое содержимое.

Assessment migration `0012_assessment` и readiness включают company_task_proposals.
Privacy очищает приватные копии предложений и зависимые command caches/outbox.
Опубликованная версия банка сохраняется restricted по существующей политике
Assessment, поэтому отправляется restricted ACK; это не полная физическая очистка.
Чтение версии банка и команды над ней проверяют текущие ограничения всех авторов.
Одобрение предложения не создаёт grade decision, не заменяет suite validation,
Evaluation или калибровку. Назначение/выполнение и отдельные результаты компаний
реализованы следующим инкрементом; см. [company-assignments.md](company-assignments.md).
Расписания/подписки и частотные ограничения реализованы далее в этом документе. Практические среды
VCV/voice/whiteboard и evidence pipeline описаны ниже.

Изменения доступны в коде/контрактах; контейнеры, .env/.secrets и внешний LLM не запускались.
Live PostgreSQL/RabbitMQ/Linux по-прежнему отложены.

### Практические среды Media и Whiteboard

Media принимает записи для активных этапов voice/VCV. До доступа к устройству
браузерный компонент вызывает `POST /media/v1/recordings/admission`: сервер проверяет
отдельное действующее согласие `recording`, текущий этап и согласие assessment.
Подписанные Privacy/Assessment RPC и локальные tombstones повторно проверяются
при загрузке, чтении и выдаче receipt. Admission не является долговременным пропуском.

`POST /media/v1/recordings` фиксирует session_id/stage_id, recording_consent_id,
mime, размер, SHA-256 и заявленную клиентом длительность. Для voice разрешены
`audio/webm`/`audio/ogg`, для VCV — `video/webm`/`video/mp4`. Одна запись на этап,
не более 32 MiB. `PUT .../{id}/chunks/{number}` принимает base64 части до 256 KiB
с отдельным SHA-256 и If-Match. Части можно передавать в произвольном порядке;
`GET .../{id}` возвращает полученные номера для возобновления. Повтор той же части
не меняет версию, несовпадение данных отклоняется. Команды используют Idempotency-Key;
кешируются ссылки, а не байты записи.

`POST .../{id}/finalize` проверяет полный набор частей, суммарный размер,
индивидуальные/общий SHA-256, сигнатуру контейнера и полное декодирование FFmpeg;
только затем создаёт неизменяемый snapshot_id. Новые байты сохраняются в закрытом
файловом хранилище, в Media БД остаются ссылки/размеры/хеши. Старые DB chunks
остаются читаемыми. Сборка и целостность повторно проверяются при выдаче.
`GET .../{id}/content` доступен только кандидату через авторизованный шлюз с
`Cache-Control: no-store`, без публичной или заранее подписанной ссылки.
Это локальное файловое хранилище: S3 backend, антивирусное сканирование и
доказанное физическое удаление из backups впереди.
Заявленная длительность/отметки клиента не считаются достоверными; сервер отдельно
фиксирует получение частей, начало и завершение загрузки.

### Проверка медиапотока и закрытое хранилище

`HR_MEDIA_STORAGE_ROOT` задаёт закрытую директорию Media (права 0700).
Без неё новая загрузка отклоняется с 503. В Compose API, consumer удаления и
transcription worker используют общий named volume `media-objects`; HTTP-сервера
файлов и публичных URLs нет. Файлы имеют права 0600 и неизменяемые ключи,
производные от subject/recording/номер части/SHA-256. Запись публикуется через
atomic link после fsync; чтение не следует symlink и проверяет размер/хеш.
Идентификатор хранилища в `.identity` закрепляется в БД: неправильный том
блокирует чтение байтов и ACK удаления. `.identity` нужно сохранять при переносе тома.

Privacy удаляет каталог кандидата, включая файлы от незавершённых транзакций,
до удаления строк и публикации ACK. При сбое файлового удаления транзакция
откатывается; повтор безопасен, поздние загрузки блокируются tombstone и
текущим Privacy admission. Обычный unlink не является доказанным стиранием
из snapshots, backups или физического носителя. Нужна отдельная retention policy.

В finalize `ffprobe` проверяет один аудиопоток; для VCV требуется также один
видеопоток. Разрешены WebM Opus/Vorbis + VP8/VP9, Ogg Opus/Vorbis,
MP4 AAC + H.264; звук 8–48 kHz и 1–2 канала, видео до 1920×1080/60 fps.
FFmpeg декодирует весь поток с остановкой при ошибке. `validation` в RecordingView
содержит серверную duration_ms, кодеки и параметры; клиентская длительность
остаётся недоверенной. Расшифровка не может заявлять длительность больше
декодированной записи с допуском 250 ms. Legacy recordings имеют validation=null
до отдельной повторной проверки; миграция не объявляет их проверенными.
Длительность декодированного потока не доказывает время реальной записи и
не заменяет Proctoring. Перед публикацией снимка повторно проверяются текущие
согласия, ограничения Privacy и срок активного этапа.

Настройки: `HR_MEDIA_FFPROBE_BINARY`, `HR_MEDIA_FFMPEG_BINARY`,
`HR_MEDIA_VALIDATION_TIMEOUT_SECONDS` (20 по умолчанию, максимум 30).
Probe и decode делят общий deadline, один слот на процесс; вывод ограничен 64 KiB,
при таймауте завершается process group. Вход использует принудительный demuxer и
только file protocol, без auto-detection playlist/сетевого ввода. Docker image
включает FFmpeg, Media container ограничен 512 MiB/1 CPU/64 PID.
Недоступный или занятый decoder возвращает 503 и не создаёт снимок/попытку
транскрибации. Ошибка содержимого возвращает 422. Это не антивирус и не отдельная
изоляция от уязвимостей декодера: hardened validation worker остаётся следующим шагом.
Миграция `0004_storage.py` сохраняет старые DB bytes и добавляет metadata/identity;
downgrade с данными или tombstones запрещён.
Отклонённую запись можно заменить до finalize через
`POST /media/v1/recordings/{id}/restart` с новым RecordingCreate, Idempotency-Key
и If-Match. Сессия/этап/согласие сохраняются; очищаются прежние части, версия
увеличивается. После finalize или завершения этапа замена запрещена. Browser
«Записать заново» поддерживает этот сценарий и повтор команды после потерянного
ответа; параметры камеры/микрофона ограничены под поддерживаемую сервером запись.
Описание параметров сверено с [FFprobe](https://ffmpeg.org/ffprobe.html) и
[FFmpeg](https://ffmpeg.org/ffmpeg.html).

Whiteboard предоставляет `POST /whiteboard/v1/boards`, `GET .../{id}` и
`POST .../{id}/operations`. Операция имеет UUID, object_id, action put/delete,
ожидаемую версию и типизированный shape: stroke/rectangle/ellipse/text.
Геометрия, размер текста, число точек/объектов и общий размер состояния ограничены;
HTML/SVG не исполняются. Операции хранятся по серверной версии и времени; дубликат
UUID не изменяет историю, пропуск версии или конфликт содержимого отклоняется.
До 100 объектов, 500 операций и 256 KiB состояния. `POST .../{id}/seal`
сохраняет immutable snapshot с SHA-256 и закрывает изменения.

Assessment запускает voice/VCV/whiteboard с серверным deadline и принимает
пару workspace_id/snapshot_id через существующий submit endpoint. Для Media
workspace_id означает recording_id, для Whiteboard — board_id. Отдельный подписанный
metadata-only receipt сверяет владельца, сессию, этап, формат, версию и digest;
байты не переносятся в Assessment, скрытые рубрики не выдаются кандидату.
После submit поздние записи/операции запрещены; сервер продвигает следующий этап.
Evaluation собирает закреплённый снимок доски или расшифровку записи через
подписанный owner API. До получения доказательств баллы отсутствуют; после сбора
доступны human review и LLM proposal. Code/SQL продолжают работать через существующие
Workspace/Runner/коллектор.

Browser ES module доступен через `/media/v1/environment.js` и
`/whiteboard/v1/environment.js`; исходник — `src/reverse_hr/assets/practical.mjs`.
`mountRecording(root, {api, sessionId, stageId, recordingConsentId, video, onReady})`
показывает controls MediaRecorder, preview, повтор записи до загрузки и возобновление
частей при сетевом сбое. `mountBoard(root, {api, sessionId, stageId, boardId, onReady})`
восстанавливает состояние, рисует canvas, добавляет текст и фиксирует снимок.
Host page передаёт callback api с текущей аутентификацией и callback onReady,
который отправляет ссылку в Assessment. Компонент не сохраняет токены.
Новая самостоятельная страница входа/кабинета этим модулем не создаётся.
Реальные камера/микрофон требуют HTTPS или localhost и разрешения браузера.

Миграции `0002_media`/`0002_whiteboard`, readiness, Gateway и workers publish/consume
в профиле all добавлены. Privacy consumer сначала очищает файловые данные Media,
затем удаляет строки частей, записей, состояний, снимков, операций, command caches
и прежний outbox в транзакции с tombstone/ACK. Откат БД не восстанавливает файлы;
повтор удаления безопасен.
Рассылка удаления уже предусмотрена общей topology. `.env`, `.secrets`, контейнеры
и внешние API не менялись; live PG/RabbitMQ/Compose по-прежнему отложены.

### Транскрибация и оценка записей/доски

Media finalize создаёт durable pending attempt. Опциональный worker `transcribe`
проверяет актуальные права и согласия до вызова провайдера и перед сохранением
результата. Расшифровка привязана к SHA-256 записи, модели и immutable transcript_id;
сегменты имеют уникальные ключи и непересекающиеся временные диапазоны.
`GET /media/v1/recordings/{id}/transcription` возвращает состояние и результат
владельцу. После ошибки повтор запускается отдельным `POST .../{id}/transcription`,
не более трёх попыток. `POST .../{id}/transcription/{attempt_id}/interrupt` отменяет
локальное ожидание; поздний ответ не сохраняется. Отмена не гарантирует отмену
списания у провайдера. Неопределённые вызовы автоматически не повторяются;
после перезапуска зависшую running attempt нужно явно прервать.

Worker выключен по умолчанию. Compose profile `transcription` использует отдельную
egress-сеть и требует `MEDIA_TRANSCRIPTION_ORIGIN`, `MEDIA_TRANSCRIPTION_MODEL` и
существующий файл `.secrets/media-transcription.key`. Для запуска вне Compose:
`HR_MEDIA_TRANSCRIPTION_ENABLED=true`, `HR_MEDIA_TRANSCRIPTION_ORIGIN`,
`HR_MEDIA_TRANSCRIPTION_MODEL`, `HR_MEDIA_TRANSCRIPTION_KEY_FILE`.
Реализован контракт операторского HTTPS gateway `POST /v1/transcribe`:
запрос `{model, recording_digest, mime, data_base64, store:false}`;
ответ `{recording_digest, model, document, cost_microusd}`. `document` содержит
`duration_ms`, `language`, `segments: [{key, start_ms, end_ms, text}]`.
Таймаут до 30 секунд, ограничение ответа 256 KiB; redirects и proxy из окружения
отключены. Это контракт адаптера: конкретный speech-провайдер ещё не подключён.
Запрет хранения должен также обеспечиваться настройками провайдера; фактическая
стоимость неизвестного/прерванного вызова требует сверки с его биллингом.

Reviewer с MFA получает `PracticalSource` через существующий review workspace.
Для voice/VCV решения содержат `recording_citations`: snapshot_id, recording_digest,
transcript_id/digest, segment_key и start_ms/end_ms внутри соответствующего сегмента.
Для whiteboard — `board_citations`: snapshot_id/digest, object_id и object_digest.
Несовпадающие снимки, хеши, объекты или диапазоны отклоняются. Авторизованный reviewer
может получить исходные части записи через
`GET /evaluation/v1/evaluation-reviews/stages/{stage_id}/recording/chunks/{number}`;
каждая выдача заново проверяет согласия и закреплённый снимок, ответ no-store.
При отзыве recording consent блокируются просмотр, подтверждение review и выдача байтов.

LLM получает ту же закреплённую расшифровку или доску и предлагает решения с
проверяемыми ссылками. Текст кандидата считается недоверенным содержимым.
Предложение не публикует баллы без human confirmation; video-анализ движений/кадров
не реализован. Prompt v2 поддерживает все форматы; уже готовые code/SQL предложения
v1 и прежние хеши human review сохраняют совместимость.
Если сбор доказательств исчерпал попытки до готовности расшифровки, reviewer может
вызвать `POST /evaluation/v1/evaluation-reviews/stages/{stage_id}/collection-retry`
с Idempotency-Key и If-Match. Команда не перезаписывает готовый source или review.
Privacy удаляет расшифровки и попытки вместе с записью; поздний ответ после удаления
не восстанавливает данные. Миграция Media `0003_transcription` добавляет новые таблицы.

Качество распознавания, реальный провайдер, камера/микрофон, декодирование контейнеров
и live PostgreSQL/RabbitMQ/Compose требуют отдельной проверки. Внешние вызовы,
секреты и рабочие контейнеры при реализации этого этапа не использовались.


### Media security и управляемые backups

Реализованы versioned private S3 adapter, ClamAV INSTREAM перед decode,
отдельный decoder container без сети/секретов с runtime attestation и cleanup
общих S3 snapshots перед completion Privacy. Основной Compose включает scanner,
freshclam и decoder; `compose.media-s3.yaml` подключает настроенные S3 buckets.
По умолчанию Media требует scanner и isolated decoder. Legacy материал без scan
receipt при включённом требовании не допускается к чтению/обработке.

Настройки, запуск, условия миграции заполненного file store и границы очистки
старых копий описаны в [docs/media-security.md](media-security.md).

## Proctoring

Реализован журнал событий самостоятельности: фокус, вкладка, вставка без содержимого,
состояние записи и технические сбои; подписи истории Media/Whiteboard/Workspace.
Повторы, пропуски, клиентские часы и поздняя доставка учитываются отдельно.
Решение reviewer с MFA привязано к версии и доказательствам; новые материалы требуют
повторного рассмотрения. Evaluation читает свежую подписанную summary, оценка
компетентности не меняется автоматически. Privacy удаляет журнал с tombstone.

### Назначения компаний: прохождение и разрешённые результаты

Цепочка company-task-proposal → pinned plan → company-assignment → session →
Evaluation → company result реализована для code, SQL, voice, VCV и whiteboard.
Кандидат до старта видит организацию-получателя; Privacy выдаёт отдельное разрешение
на баллы именно этого задания. Отказ, истечение и отзыв защищены версиями и повторами.
Сессия компании не получает grade policy, не меняет общий грейд и не раскрывает контакты.

Evaluation использует существующие доказательства Runner/практических сред и LLM
proposal с человеческой проверкой. Участник назначившей компании не может утвердить
её баллы. Компания получает только актуальные проверенные баллы этапов/критериев;
Privacy/Employer/Evaluation перепроверяются при каждом чтении. Кандидат завершает
назначение после проверки всех этапов; отзыв разрешения закрывает экспорт компании.

Новые миграции Assessment `0013_assessment` и Privacy `0008_privacy`, runtime OpenAPI,
readiness и удаление включены. Порядок запросов и границы этапа:
[company-assignments.md](company-assignments.md). Подписки, расписания, частота,
уведомления и worker: [company-schedules.md](company-schedules.md).
Пользовательские экраны этой цепочки ещё требуют интеграции с API.

### Подписки и расписания заданий компаний

## Privacy-архив, Audit, условия подбора и внешние уведомления

Расширен backend четырёх продуктовых блоков. Privacy собирает собственные данные
всех 17 владельцев через подписанные страницы, включая ответы Code/SQL, PDF и
медиа из File/S3. Манифест и цепочка страниц проверяются при скачивании;
отзыв разрешения и удаление закрывают доступ. Снимки фиксируются отдельно по
владельцам. Старый `/export` теперь явно обозначает частичную проекцию.
Исправления профиля, контактов, резюме, предпочтений, самозаявленных достижений
и настроек уведомлений защищены версиями и квитанциями исполнения.

Audit получает события отдельным consumer, хранит исходные подписанные доказательства
в подписанной цепочке и предоставляет расследование с MFA и ролью `audit_reviewer`.
Выдача контактов, PDF, передача в ATS и попытки email-доставки создают Audit-событие
через транзакционный outbox владельца. Удаление персональных полей само подписано;
срок хранения настраивается. Для обнаружения полного отката БД нужен внешний
свидетель контрольных точек.

Matching сравнивает явно подтверждённую зарплату, формат работы и окно выхода.
Это самоописание кандидата, отдельно от проверенных навыков. Условия вакансии,
Need и приглашения согласованы. Старые вакансии без типизированных условий
сохраняют прежнее поведение до явного обновления компанией.

Email-доставка использует проверенный адрес, отдельные согласия на служебные
сообщения и маркетинг, идемпотентный провайдер, leases, ограниченные повторы
и подписанный публичный callback. В письме только общее уведомление и ссылка
в кабинет. Исторические уведомления не отправляются после нового согласия.
По умолчанию отправка выключена. Необязательный `compose.notification-email.yaml`
подключает настроенного провайдера и worker `notification-delivery`.

Identity экспортирует собственный аккаунт и метаданные способов входа из Keycloak
через необязательный read-only адаптер. `compose.identity-export.yaml` подключает
источник; без него общий архив явно неполон, а недоступный включённый источник
не позволяет завершить архив. Секреты способов входа не выгружаются.

Новые миграции: Candidate `0007_candidate`, Privacy `0010_privacy`,
Notification `0006_notification`, Audit `0002_audit`.
Подробнее: [Privacy](data-subject-requests.md), [Audit](audit-journal.md),
[условия Matching](matching-employment-conditions.md),
[email](external-notifications.md), [Identity](identity-export.md).
