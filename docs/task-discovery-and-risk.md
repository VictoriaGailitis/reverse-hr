# Подбор новых заданий, актуальность достижений и сигналы риска

## Рекомендации заданий

Кандидат выдаёт отдельное согласие `task_recommendations` в Privacy и включает подписку в разделе прохождения. Можно указать стек и минимальный интервал уведомлений (1–168 часов, по умолчанию 24). При пустом стеке используются сохранённые навыки профиля. Подбор работает и без публикации профиля компании.

Worker Candidate `recommend-tasks` опрашивает подписанный, постраничный каталог Assessment. Сейчас каталог включает опубликованные общие собственные референсы с готовым проверенным вариантом; закрытые задания компаний остаются в отдельном механизме назначений и подписок компаний. Метаданные содержат направление, уровень, формат и явно написанные оператором `stack_tags`, без ответов и скрытых тестов. Пустые теги означают общее задание по направлению, а не предположение о стеке.

Задание должно совпасть с любой активной специализацией и её подтверждённым уровнем; если уровень ещё не подтверждён, используется заявленный как интерес. Все теги задания должны входить в стек кандидата. Рекомендация никогда не подтверждает грейд. Новая версия референса считается новым предложением; отдельные варианты одного референса не создают повторные уведомления.

Подписка и рекомендация фиксируются транзакционно вместе с outbox-событием. Уникальность `(candidate_id, version_id)`, блокировка субъекта и повторная проверка версии подписки защищают от дублей и гонок с отменой. После ошибки RPC повтор через пять минут; после полного обхода каталог проверяется снова через пять минут. Частота отправки сохраняется между перезапусками.

Notification получает `candidate.task_notification_requested.v1`. Рекомендации относятся к категории marketing: в приложении нужны `in_app` и `marketing_in_app`, для email — отдельные настройки и действующее согласие на внешний маркетинг. При каждом чтении и отправке проверяются подписка, согласие, текущий профиль и доступность задания. Отмена/отзыв согласия прекращают выдачу; Privacy удаляет подписку, историю рекомендаций и их локальные события. Данные входят в общий экспорт Privacy.

API Candidate: `GET/PUT /v1/candidates/me/task-subscription` (первичная версия `If-Match: "0"`), `GET /v1/candidates/me/task-recommendations?after=UUID`. Внутренние API: Assessment `/internal/v1/market/task-catalog`, Candidate `/internal/v1/market/task-notice`; подпись, привязка запроса, nonce и ограничение размера обязательны.

## Устаревание бонуса достижений

Подтверждённое, разрешённое и релевантное достижение даёт 2 балла при возрасте 0–364 дней, 1 балл при 365–729 днях, 0 с 730-го дня. Будущая или отсутствующая дата не даёт бонуса. Командные и индивидуальные достижения учитываются одинаково, зеркальные результаты дедуплицируются; общий бонус ограничен 5 баллами либо меньшим лимитом утверждённой политики.

Возраст считается по текущей дате UTC при каждом подборе и чтении сохранённого результата. Устаревший сохранённый матч скрывается, если актуальное объяснение/баллы изменились; новый поиск рассчитает актуальное ранжирование. История достижения сохраняется, подтверждённый грейд не меняется. Это явная продуктовая настройка MVP, не экспертно откалиброванная модель результативности.

## Риски и дополнительная проверка

Детерминированный детектор `prompt-risk-v1` проверяет отправленный код/SQL, текст доски и транскрипты голоса/видео: попытки отменить инструкции, подменить системную роль, извлечь системный промпт или навязать оценку. Нормализуются Unicode и невидимые форматирующие символы. Само упоминание prompt injection не является сигналом. Цитата атаки в учебном ответе может вызвать подозрение: независимый человек может отклонить его с обоснованием. Детектор не гарантирует обнаружение всех обходов.

Evaluation сохраняет коды, версию правил, этап и хеш источника, без копирования текста ответа. Один этап регистрируется один раз. Сигналы накапливаются по кандидату между сессиями; подтверждённое человеком состояние Proctoring `concern` тоже регистрируется. Сырые события фокуса сами по себе не объявляют нарушением.

Открытый риск останавливает вызов модели и автоматическую проверку этапов. Подписанный StageScore сообщает Assessment, что требуется дополнительная проверка: автоматическое присвоение грейда также направляется человеку. Существующий грейд и баллы за навыки не снижаются. Кандидат видит состояние своей проверки, независимый проверяющий с MFA — очередь и объяснимые коды.

Проверяющий может отклонить подозрение, потребовать отдельную проверку или подтвердить её выполнение. Для последнего требуется другой этап этого кандидата, поступивший после регистрации риска и оценённый человеком с проверяемыми доказательствами; тот же этап, отсутствующее доказательство или автоматическая оценка не подходят. Каждый риск закрывается отдельно. Изменения требуют версии и idempotency key; перепроверка прав выполняется и при повторе команды. Удаление данных/проверяющего учитывается через Privacy.

В чате работодателя тот же детектор дополняет существующий журнал рисков и очередь независимой модерации. Сообщения чата не передаются LLM. Сигналы диалога не являются автоматическим основанием менять грейд или навешивать публичную метку «читер».

API Evaluation: `GET /v1/evaluation-risks/me`, `GET /v1/evaluation-risks/queue?after=UUID`, `POST /v1/evaluation-risks/{stage_id}/decision` с `dismiss`, `require_verification` или `complete_verification`. Интерфейс — раздел очередей автоматической оценки. Источник и решение защищены правами и согласиями; события Audit содержат только ссылки.

## Linux и Docker

Миграции: Candidate `0009_candidate`, Evaluation `0010_evaluation`. После обновления примените обычные миграции сервисов и обновите RabbitMQ topology через `scripts/configure_events.py` по основной инструкции. Worker `candidate-task-discovery` включён в профиль Compose `all`:

```bash
docker compose --profile all up -d --build
```

Для запуска worker на Linux без контейнера после миграций:

```bash
HR_SERVICE_NAME=candidate uv run python -m reverse_hr.platform.worker recommend-tasks
```

Нужны обычные настройки БД Candidate, URL Assessment/Privacy и ключи подписи. Полный порядок настройки инфраструктуры и секретов — в [Linux deployment](linux-deployment.md). Реальный внешний email требует настроенного провайдера; правила риска и старения бонусов работают без внешнего LLM.
