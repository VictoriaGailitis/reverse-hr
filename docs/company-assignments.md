# Задания компаний

Assessment продолжает существующий конструктор всех пяти форматов. Назначение
использует опубликованную версию предложения компании и опубликованный план,
закрепляющий именно эту версию. Для критериев `test_result` действует существующий
допуск скрытых наборов и Runner; сам факт назначения не заменяет проверку набора.
Все пакеты и разрешения пока относятся к demo-сценарию.

## Порядок вызовов

1. Компания создаёт и отправляет `company-task-proposals`; независимый
   `content_admin` с MFA утверждает неизменяемую версию. Затем через существующий
   `POST /v1/assessment-plans` публикуется план этой версии, с выбором проверенных
   test suites при необходимости.
2. Сотрудник проверенной компании вызывает `POST /v1/company-assignments`:
   `organization_id`, `candidate_id`, `proposal_id`, `plan_version_id`,
   `expires_in_days` (1–90, по умолчанию 14). Допущены owner/recruiter/technical_expert
   через свежий подписанный Employer content-membership. Активный дубль для той же
   компании, кандидата и плана отклоняется. Ответ показывает получателя результата,
   форматы, длительность и границы выдачи до начала прохождения.
3. Кандидат смотрит `GET /v1/company-assignments/{id}` или собственный список.
   Список компании требует `organization_id` и действующее членство; обе выдачи
   ограничены 50 записями, следующий запрос использует `after` UUID последней записи.
   Кандидат может вызвать `POST .../{id}/decline`, компания — `POST .../{id}/revoke`
   для ещё не принятого назначения. Отказ не создаёт grade decision или cooldown.
4. Кандидат получает отдельные согласия `assessment` и
   `company_result_disclosure` через Privacy `POST /v1/consents` с актуальной версией
   из `GET /v1/consents/policies` (сейчас `demo-v1`). Затем создаёт
   `POST /v1/company-result-grants`: `assignment_id`, `organization_id`, `consent_id`,
   `expires_in_days` (1–90, по умолчанию 30). Это разрешение только на проверенные
   баллы конкретного задания для конкретной организации.
5. `POST /v1/company-assignments/{id}/accept` с `assessment_consent_id` и
   `result_grant_id` атомарно создаёт обычную Assessment session в `preflight`.
   `grade_policy_id` в этом запросе отсутствует и не принимается. Принятие проверяет
   точную привязку разрешения, срок назначения, публикацию предложения/плана/контента,
   private suite pins и отсутствие другой активной сессии. Повтор возвращает ту же
   сессию после повторной проверки доступа.
6. Кандидат использует существующие session start → stage start → среда → submit.
   Code/SQL закрепляют coding snapshot; voice/VCV — проверенную запись; whiteboard —
   закрытый снимок доски. Для записи требуется отдельное согласие `recording`.
7. Evaluation получает подписанные материалы и артефакты, принимает доказанные
   результаты Runner, при настройке провайдера — LLM proposal, и требует человеческую
   проверку критериев. `assessment_reviewer` с MFA не может проверять собственную
   сессию или задание компании, действующим сотрудником которой он является.
8. `GET /v1/company-assignments/{id}/result` доступен кандидату и допущенным
   сотрудникам назначившей компании. До проверки всех этапов возвращает
   `review_pending` с пустым `stages`; после — `reviewed`, баллы этапов и критериев,
   competency keys и review IDs. Выдача заново проверяет Privacy разрешение,
   processing/assessment consent, Employer membership, подписи и привязки Evaluation
   к точным снимкам и рубрикам. Недоступный сервис или неверная подпись закрывают выдачу.
9. Кандидат завершает `POST .../{id}/complete` после проверки всех этапов человеком.
   Назначение и сессия атомарно переходят в `completed`; повтор безопасен.
   Закрытие не создаёт общий грейд. Компания продолжает получать актуальный проверенный
   результат через тот же защищённый endpoint.

Все POST-команды требуют `Idempotency-Key`; переходы по существующему объекту также
требуют актуальный `If-Match`. Конфликт версии/состояния — 409. Ответы содержат
`Cache-Control: no-store`. В command cache назначения хранятся только UUID-указатели.

## Ограничение выдачи

Компания не получает исходники, записи, транскрипты, доску, ответы эталона,
скрытые тесты, rationale/citations проверяющего, его личный ID или контакты кандидата.
Баллы компании не меняют общий подтверждённый грейд и его retry/cooldown; в company
session не привязывается grade policy. Контакты выдаются только отдельной цепочкой
Hiring/Privacy и не открываются принятием или завершением задания.

Кандидат смотрит и отзывает разрешение через
`GET /v1/company-result-grants/{id}` и `POST .../{id}/revoke`. Истечение, отзыв
разрешения или базового согласия немедленно закрывают следующий экспорт компании,
включая повтор ранее успешной команды принятия. Кандидат сохраняет доступ к своему
результату при действующем согласии assessment. Истечение срока назначения закрывает
новое принятие; уже начатая сессия сохраняет свои закреплённые этапы и дедлайны.
Отзыв контента/плана также закрывает новые допуски, сохраняя снимки начатых сессий.

Privacy deletion удаляет назначения кандидата, command caches и assignment outbox;
его сессии и evidence очищаются существующими Assessment/Evaluation/environment
consumers. Privacy tombstone немедленно закрывает разрешения; после завершения
каскадной очистки локальные result grants удаляются. Если удаляется автор назначения
другого кандидата, неизменяемая привязка получателя сохраняется restricted, а доступ
через автора закрывается. Удаление не превращает company session в общий экзамен.

Миграции: Assessment `0014_assessment`, Privacy `0008_privacy`, Notification `0003_notification`. Readiness проверяет
новые таблицы и актуальную версию схемы; downgrade отказывает до изменения схемы,
если сохраняются данные назначений/разрешений или защищённая история предыдущих этапов.

## Проверки и границы этапа

`tests/test_company_assignments.py` проверяет API назначения, Privacy scope,
повторы/конфликты, отказ/отзыв/сроки, удаления, независимость reviewer и сквозную
подписанную выдачу всех пяти форматов. Сквозные Code/SQL-сценарии используют артефактную
рубрику; отдельная проверка назначения подтверждает сохранение runtime-admitted
private suite pins. Скрытые наборы, Runner proofs и LLM проверяются также существующими
интеграционными тестами общей регрессии. Сериализация обычного PinnedMaterial
сохранена совместимой с ранее записанными Evaluation records: новый company scope
присутствует только у назначенных сессий. Media API-тесты используют синтетические байты
и тестовый decoder/speech adapter; реальные декодеры имеют отдельные проверки.

Расписания, подписки, частотные ограничения и уведомления описаны в
[company-schedules.md](company-schedules.md). Для пользовательских экранов доступен API.
Живой прогон PostgreSQL/RabbitMQ/Compose, реальные устройства и production-провайдеры
остаются отдельной проверкой; внешняя инфраструктура в этом инкременте не менялась.
