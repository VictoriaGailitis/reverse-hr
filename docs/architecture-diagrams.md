# Архитектура Reverse HR

Схемы описывают текущий код после реорганизации бэкенда. Обзор продукта и запуск — в [README](../README.md), расположение модулей — в [структуре бэкенда](backend-structure.md), правила доступа и владения — в [архитектурных правилах](architecture.md).

Система имеет 17 основных сервисов и три демосервиса: `demo-fsp`, `demo-codenrock`, `demo-ats`. У основных сервисов отдельные процессы, БД, роли доступа и миграции. Исходники, Docker-образ и зависимости общие; независимых версий сборки каждого сервиса пока нет. Схемы показывают логические границы, а не число физических серверов.

## 1. Развёртывание, транспорт и внешние зависимости

```mermaid
flowchart TB
    USER["Браузер: React / TypeScript"]
    WEB["Frontend Nginx: собранная SPA, proxy /api"]
    AUTH["Keycloak: пользователи, сессии, MFA"]
    GW["Nginx API gateway"]
    USER -->|"OIDC Authorization Code + PKCE"| AUTH
    USER -->|"SPA и API с access token"| WEB
    WEB -->|"API / удаление префикса /api"| GW
    subgraph APP["Процессы сервисов / контейнеры Compose"]
        API["17 FastAPI API: собственные маршруты и права"]
        JWT["Проверка JWT / JWKS, роли, членство, согласия"]
        RPC["Внутренние HTTP API: Ed25519, срок, nonce, привязка ответа"]
        OUT["Publisher: transactional outbox"]
        CON["Consumers: inbox, дедупликация, версии событий"]
        JOB["Workers: задания, оценки, PDF, доставка, Privacy, SLA"]
        API --> JWT
        API --> RPC
    end
    GW --> API
    JWT -->|"JWKS"| AUTH
    RPC -->|"запрос владельцу данных"| API
    subgraph DATA["Локальная инфраструктура данных"]
        PG[("PostgreSQL: БД каждого сервиса, свои credentials")]
        MQ["RabbitMQ: exchanges events.*, очереди сервисов, retry / DLQ"]
        FILE[("Закрытые файловые хранилища")]
    end
    API -->|"доменные данные + outbox в одной транзакции"| PG
    OUT -->|"читает локальный outbox"| PG
    OUT -.->|"подписанная доставка"| MQ
    MQ -.-> CON
    CON -->|"локальная транзакция: inbox + изменения"| PG
    JOB -->|"локальные задания / leases / результаты"| PG
    JOB --> RPC
    API --> FILE
    subgraph ISOLATION["Обработка недоверенных данных"]
        LINUX["Отдельный Linux-узел: Runner supervisor + NsJail"]
        MEDIA["Изолированный декодер видео / аудио"]
        PDF["Изолированный PDF / OCR guest"]
        AV["ClamAV"]
    end
    JOB --> LINUX
    JOB --> MEDIA
    JOB --> PDF
    JOB --> AV
    subgraph OPTIONAL["Подключаемые провайдеры"]
        LLM["LLM: генерация Assessment, Evaluation и разбор запросов Matching"]
        TRANS["Транскрипция"]
        S3[("S3: медиа и настроенные архивы резервных копий")]
        DELIVERY["HTTPS-провайдер уведомлений / callbacks"]
        SOURCES["Источники достижений / ATS"]
    end
    JOB --> LLM
    JOB --> TRANS
    JOB --> S3
    JOB --> DELIVERY
    JOB --> SOURCES
```

Сплошные стрелки — запросы и доступ к ресурсам; пунктирные — асинхронные события. API и workers используют только БД своего сервиса. RabbitMQ обеспечивает повторную доставку; outbox/inbox и бизнес-проверки нужны для безопасной обработки дублей и запоздавших изменений. Необработанные события доступны для диагностики и повторной обработки через очереди ошибок.

Docker-сценарий запускает собранный фронтенд через `compose.frontend.yaml`; Nginx фронтенда раздаёт SPA и проксирует `/api/` в gateway. В Compose PostgreSQL общий как сервер, но базы и роли разделены. Целевая среда развёртывания — Linux. Пользовательский код выполняется на выделенном Linux-узле или в отдельной Linux-VM; установка и подключение к платформе описаны в [Runner](../infra/runner/README.md), общий запуск — в [инструкции Linux](linux-deployment.md). Профиль `all` не подключает автоматически S3, LLM и транскрипцию. Демоисточники заменяют внешние API только на демонстрационном стенде. Mailpit принимает локальную почту, в том числе Keycloak; внешняя доставка Notification имеет отдельный HTTPS-протокол.

## 2. Структура кода и границы зависимостей

```mermaid
flowchart TB

        CONSUMER["consumer.py: бизнес-обработка событий"]

        APP --> DOMAIN
        CONSUMER --> DOMAIN
        DOMAIN --> HELPERS
    end
    PLATFORM["platform/: HTTP bootstrap, worker, settings, lazy registry, migrate"]
    COORD["coordination/: Privacy owner-dispatch и review SLA"]
    PROTO["protocols/: подписанные клиенты и HTTP-адаптеры владельца"]
    TYPES["contracts/: DTO, события, доказательства, чистые проверки"]
    SHARED["shared/: JWT, подписи, транспорт, DB, файлы, изоляция"]
    COMPOSE --> APP
    COMPOSE --> PLATFORM
    APP --> PLATFORM
    PLATFORM -.->|"выбирает сервис / consumer по имени"| CONSUMER
    PLATFORM -.->|"выбирает цепочку миграций"| MIG
    DOMAIN --> PROTO
    DOMAIN --> TYPES
    DOMAIN --> SHARED
    CONSUMER --> COORD
    COORD --> PROTO
    PROTO --> TYPES
    PROTO --> SHARED
```

Стрелки показывают основные зависимости и сборку, а не полный граф Python-импортов. HTTP-адаптер протокола работает в процессе владельца и может использовать его локальные модели. Общая транспортная миграция находится в `platform/migrations/versions/`; бизнес-таблицы — в миграциях соответствующего сервиса. Старые revision IDs сохранены.

Прямые импорты реализации другого сервиса запрещены [архитектурными тестами](../tests/shared/test_architecture.py). `shared/` и `contracts/` не импортируют внутренние модули сервисов. Внутри `domain/` маршруты, ORM и бизнес-операции пока не полностью разделены на слои; перенос каталогов не означает завершённую переработку этой внутренней структуры.

## 3. Прохождение, доказательства, оценка и подтверждённый грейд

```mermaid
sequenceDiagram
    actor C as Кандидат
    participant A as Assessment
    participant W as Coding Workspace / Media / Whiteboard
    participant R as Code Runner
    participant E as Evaluation
    participant L as LLM-провайдер
    actor H as Проверяющий
    participant P as Candidate
    participant M as Matching
    C->>A: Создать сессию / выбрать допустимый вариант
    A->>A: Закрепить контент, рубрику, тесты и правила попыток
    C->>W: Решение, запись или операции доски
    W->>W: Сохранить материал и неизменяемый снимок
    C->>A: Отправить этап со ссылкой на снимок
    A->>W: Проверить снимок через подписанный API
    A-->>R: stage_submitted через outbox / RabbitMQ
    A-->>E: stage_submitted через outbox / RabbitMQ
    R->>A: Получить отдельный допуск к снимку и закреплённым тестам
    R->>W: Получить разрешённый отправленный снимок
    R->>R: Выполнить скрытые тесты в допущенном NsJail runtime
    E->>R: Получить и проверить подписанные результаты
    E->>W: Получить разрешённые материалы этапа
    opt Подключён провайдер LLM
        E->>L: Оценка по закреплённой рубрике
        L-->>E: Предложенная оценка и обоснование
    end
    E->>E: Проверить цитаты и согласие двух предложений, баллы тестов только из Runner
    alt Доказательства полны, политика калибрована, результат вне границ
        E->>A: Подписанная автоматическая оценка этапа
        A->>A: Автоматическое решение по закреплённой шкале
    else Неопределённость, расхождение или граница грейда
        H->>E: Проверить доказательства и оценку этапа
        H->>A: Подтвердить итоговое решение с обоснованием
    end
    A->>A: Проверить калибровку, политику, cooldown и полномочия
    A-->>P: grade_decision_recorded
    P->>A: Проверить решение через подписанный API
    P->>P: Обновить подтверждённый грейд с учётом версии
    P-->>M: profile_updated
    M->>P: Получить разрешённую актуальную проекцию
    M->>M: Обновить индекс и объяснения подбора
```

Пунктирные сообщения с именами событий проходят через брокер; остальные — действия пользователя или запросы. Для кода/SQL участвует Runner, для остальных форматов — соответствующие материалы и доказательства. Evaluation хранит оценки этапов и предложения LLM; Assessment владеет итоговым решением, правилами попыток и апелляциями. Candidate хранит подтверждённый грейд профиля, Matching — его поисковую проекцию.

Proctoring собирает сигналы от среды прохождения и клиента; результаты проверки самостоятельности доступны в процессе рассмотрения. Они не меняют грейд автоматически. Апелляция создаётся в Assessment, рассматривается независимым проверяющим с повторной проверкой доказательств и завершается новым решением либо сохранением прежнего. Изменённое решение проходит ту же цепочку Candidate → Matching; уведомления идут через Notification.

## 4. Подбор, вакансии, найм и интеграции

```mermaid
flowchart TB
    CO["Компания / рекрутер"]
    C["Кандидат"]
    EMP["Employer: членство, верификация, ограничения"]
    MATCH["Matching: фильтры, квалификация, объяснения"]
    CAN["Candidate: профиль, подтверждённый грейд, резюме"]
    ACH["Achievements: разрешённые подтверждённые достижения"]
    HIRE["Hiring: вакансии, потребности, отклики, приглашения, диалоги"]
    PRIV["Privacy: публикация, результаты, контакты, ATS"]
    INT["Integration: доставки, адаптеры, callbacks"]
    ATS["Внешняя ATS / demo-ats"]
    SRC["ФСП / Codenrock / демоисточники"]
    NOT["Notification: настройки и доставка"]
    CO -->|"запрос и условия"| MATCH
    CO -->|"вакансия / приглашение / диалог"| HIRE
    C -->|"отклик / принятие / отказ / диалог"| HIRE
    MATCH -->|"права компании"| EMP
    HIRE -->|"права компании"| EMP
    MATCH -->|"разрешённая проекция без контактов"| CAN
    MATCH -->|"потребности и требования"| HIRE
    MATCH -->|"ограниченный политикой бонус"| ACH
    MATCH --> PRIV
    HIRE -->|"проверка доступа при выдаче"| PRIV
    HIRE -->|"разрешённое резюме / контакты"| CAN
    CAN -->|"актуальное разрешение при скачивании"| PRIV
    HIRE -.->|"принятое приглашение"| PRIV
    HIRE -.->|"запросы уведомлений"| NOT
    HIRE -->|"разрешённая передача"| INT
    INT -->|"проверка согласия каждой попытки"| PRIV
    INT --> ATS
    ATS -->|"callback"| INT
    INT -.->|"ats_status_changed"| HIRE
    INT -->|"импорт"| SRC
    ACH -->|"данные источника"| INT
```

Публикацией вакансий, самостоятельными откликами и процессом найма владеет Hiring; Matching хранит поисковые проекции и подборки. Фильтры учитывают специализацию, грейд, требования, зарплату, формат работы и доступность. Принятие приглашения запускает оформление разрешения; выдача контактов и документов всё равно проверяет актуальный доступ. ATS получает только разрешённые данные, а её callbacks не обходят проверки переходов и версий.

Задания компаний находятся в Assessment: конструктор → назначение → прохождение → оценка → разрешённый результат. Подписки, разовые/регулярные расписания и лимиты обрабатывает worker Assessment; перед назначением проверяются актуальные права и согласия. События нового задания, срока и готового результата передаются в Notification. Технический эксперт компании получает только разрешённый результат, а не весь архив материалов кандидата.

## 5. Privacy, удаление, выгрузки и Audit

```mermaid
sequenceDiagram
    actor C as Кандидат
    participant P as Privacy
    participant S as Сервисы-владельцы данных
    participant Q as RabbitMQ
    participant B as Хранилища и настроенные backup-архивы
    participant A as Audit
    C->>P: Отозвать согласие / ограничить обработку
    P->>P: Сохранить актуальное состояние и версию
    S->>P: Проверить разрешение при запросе или доставке
    P-->>S: Запрет после отзыва / ограничения
    P->>Q: Событие изменения через transactional outbox
    Q-->>S: Удалить проекции / отменить устаревшие действия
    opt Выгрузка или исправление
        C->>P: Создать обращение
        P->>S: Подписанные запросы владельцам, страницы данных
        S-->>P: Разрешённые данные / результат исправления
        P->>P: Собрать общий архив и статус обращения
        C->>P: Получить свой готовый архив
    end
    opt Удаление данных
        C->>P: Запросить удаление
        P->>Q: deletion_requested
        Q-->>S: Доставить запрос владельцам
        S->>S: Очистить свои данные и отменить связанные задания
        S->>B: Удалить собственные файлы и объекты
        S->>Q: Подтвердить удаление / ограничение
        Q-->>P: Сохранить подтверждения владельцев
        P->>B: Worker purge-backups: удалить зарегистрированные снимки кандидата
        B-->>P: Подтвердить отсутствие копий
        P->>P: Завершить обращение после ACK и очистки архива
    end
    S->>Q: Подписанные audit-события действий и раскрытий
    Q-->>A: Consumer защищённого журнала
    A->>A: Проверить доказательства, сохранить историю
```

Оперативный запрет доступа основан на актуальной проверке Privacy, а не на ожидании доставки события. События очищают проекции и останавливают фоновые процессы; ответы владельцев позволяют отслеживать выполнение обращения. Выгрузка собирается через API с пагинацией, без SQL-доступа Privacy к чужим БД. Очистка управляемых резервных копий требует настройки поддерживаемых хранилищ и областей удаления; схема не означает автоматическую очистку любых внешних бэкапов.

Audit — отдельный consumer и сервис поиска истории с ограничениями доступа. Он сохраняет доказательства значимых действий и раскрытий; проверки Privacy применяются и к доступу к пользовательским данным журнала. Политики хранения, удаления и ограничения описаны в [Audit](audit-journal.md) и [обращениях Privacy](data-subject-requests.md).

## 6. Медиа, PDF и изолированная обработка

```mermaid
flowchart TB
    C["Кандидат"]
    MEDIA["Media: видео / голос, загрузка, метаданные"]
    CAN["Candidate: импорт и генерация резюме"]
    STORE[("Закрытые исходные объекты: файлы; для Media также S3")]
    AV["Антивирусная проверка ClamAV"]
    MD["Изолированный медиадекодер"]
    PD["Изолированный PDF guest: текст / OCR"]
    TR["Подключаемая транскрипция"]
    MAT["Media: проверенные материалы / транскрипт"]
    DRAFT["Candidate: предложенные поля профиля"]
    CONF["Подтверждение кандидатом"]
    RESUME["Полный / обезличенный PDF с текстовым слоем"]
    EVAL["Evaluation: доступные доказательства этапа"]
    COMPANY["Компания: разрешённый вариант резюме"]
    PRIV["Privacy: актуальные согласия и разрешения"]
    C --> MEDIA
    C --> CAN
    MEDIA --> STORE
    CAN --> STORE
    STORE --> AV
    AV -->|"проверенный объект"| MD
    AV -->|"проверенный PDF"| PD
    MD --> MAT
    MAT --> TR
    TR --> MAT
    PD --> DRAFT
    DRAFT --> CONF
    C --> CONF
    CONF --> RESUME
    MAT -->|"подписанный API"| EVAL
    RESUME -->|"проверка каждого скачивания"| PRIV
    PRIV -->|"разрешённая выдача через Candidate"| COMPANY
```

Это логический конвейер; декодеры работают с ограничениями сети, файловой системы и ресурсов. Непроверенные или отклонённые объекты не становятся доступными доказательствами. Согласие на запись не означает согласие на публикацию записи компании. Извлечённое самоописание подтверждается кандидатом и не превращается в проверенный навык; эти данные отделены от результата Assessment.

## Что схемы не подтверждают

Схемы описывают реализованные компоненты и механизмы подключения. Экспертная калибровка, утверждение рабочих политик, реальные LLM/транскрипция/внешние источники и полная приёмка стенда требуют данных и настройки. Реорганизация файлов не обновляет работающие контейнеры: необходима пересборка. Изменение исходников Linux Runner меняет fingerprint и требует повторных проверок и нового допуска runtime. Подробности — в [отчёте Runner](../infra/runner/LOCAL-VERIFICATION.md).


## 7. Генерация оригинальных заданий и пополнение пула

    LLM --> STRUCT["Проверка схемы, критериев, ограничений и близких дублей"]

    POOL --> SELECT["Выбор варианта: предел выдач и cooldown семейства"]
    SELECT --> PIN["Сессия закрепляет контент, рубрику и проверенные тесты"]
    CAL["Экспертная калибровка конкретной версии референса"] --> POLICY["Утверждённая политика автоматического грейда"]
