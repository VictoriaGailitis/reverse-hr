# Выбор и вариативность заданий

Механизм использует утверждённые альтернативные `PlanVersion`: каждая альтернатива уже содержит
семейства, конкретные версии заданий, порядок этапов и закреплённые скрытые тесты. Сервер выбирает
целый план из банка допустимых комбинаций. Он не собирает произвольные комбинации на лету и не
меняет тесты, рубрики или сложность после начала сессии. Контент остаётся явно демонстрационным;
сопоставимость реальной сложности требует отдельной экспертной калибровки.

## Политика выбора

Администратор с MFA создаёт `POST /v1/assessment-selection-policies`:

```json
{
  "name": "Backend Junior: альтернативные семейства",
  "plan_version_ids": ["UUID первого плана", "UUID второго плана"],
  "family_cooldown_seconds": 86400,
  "variant_cooldown_seconds": 2592000,
  "window_seconds": 2592000,
  "family_candidate_limit": 2,
  "family_global_limit": 1000,
  "candidate_session_limit": 10
}
```

Нужны минимум два уникальных опубликованных плана. Проверяется одинаковая специализация, грейд,
порядок форматов, длительность, наличие уточнений и структура критериев по компетенциям/баллам/
типам доказательств. Это структурная проверка, а не доказательство равной сложности.
Другой администратор утверждает политику через `/{policy_id}/publish` с `If-Match` и обоснованием.
Опубликованные параметры неизменяемы. `/{policy_id}/retire` закрывает дальнейший выбор по этой
политике; новая редакция создаётся как новый ресурс. Все команды требуют `Idempotency-Key`.
Приватную конфигурацию читает администратор через `GET /{policy_id}`.

Для оцениваемых сессий `grade_policy_ids` задаёт отображение **каждого** ID плана в его собственную
утверждённую политику грейда. Проверяются привязка к плану, калибровка и статус утверждения.
Выбранная сессия автоматически получает соответствующую политику. Прямой запуск такого плана
без неё отклоняется. Ротация не отменяет существующие cooldown повторной оценки и смены грейда.

Кандидат получает предложения через `GET /v1/assessment-selection-policies`: только ID, название,
специализацию, грейд и demo-маркер. `POST /v1/assessment-selected-sessions` принимает
`selection_policy_id`, `assessment_consent_id` и `Idempotency-Key`. Кандидат не задаёт семейство,
вариант или параметры генерации. Порядок выбора:

1. Меньше предыдущих выдач кандидату из этих семейств.
2. Меньше выдач конкретных версий заданий.
3. Более давняя последняя выдача этих семейств.
4. Меньше глобальных выдач семейств и версий в текущем окне.
5. Стабильный ID плана при равенстве предыдущих условий.

Отклоняются альтернативы с исчерпанными лимитами, отозванным контентом/планом, недействительными
скрытыми тестами или неподходящей политикой грейда. Недоступность Privacy и ошибки авторизации
не маскируются под отсутствие вариантов. При исчерпании банка возвращается 409: сроки и лимиты
автоматически не ослабляются.

Ограничения распространяются на семейства из опубликованных политик также при прямом
`POST /v1/assessment-sessions` и принятии задания компании. Считаются все уже созданные сессии,
включая отменённые: кандидат не может многократно открывать и отменять их ради нового задания.
Окна скользящие, граница cooldown доступна ровно после истечения срока. Глобальная частота
проверяется в той же транзакции, что и создание сессии; опубликованные политики блокируются
`FOR UPDATE` в PostgreSQL. SQLite может вернуть 503 при конкурирующей записи; повтор безопасен.

В выбранной сессии сохраняются ID, снимок правил и SHA-256 политики. API возвращает квитанцию
`selection`; повреждённый снимок отклоняется. Версии задач, рубрик и тестов остаются закреплёнными.
Повтор того же запроса возвращает существующую сессию с её текущим статусом, даже после отмены
или вывода политики из использования.

## Параметризованные варианты

`POST /v1/assessment-variant-templates` принимает опубликованную базовую версию и
`allowed_parameters`, например `{"size": ["10", "20"], "domain": ["orders", "events"]}`.
В тексте условия и эталона используются буквальные маркеры `{{size}}`, `{{domain}}`.
Список объявлений должен точно совпадать с используемыми параметрами. Максимум 12 параметров,
20 разрешённых значений для каждого, 200 символов на значение. Шаблон читает только content_admin
с MFA через `GET /v1/assessment-variant-templates/{template_id}`.

Независимый администратор утверждает шаблон через `/{template_id}/publish`. После этого
`/{template_id}/generate` принимает `parameters` и ожидаемую `family_version`. Подстановка
буквальная, без выполнения кода или выражений. Рубрики, компетенции, формат, продолжительность
и связи уточнений сохраняются. Неизвестные/недостающие параметры и значения вне утверждённых
границ отклоняются. Смена версии семейства требует повторного чтения актуальной версии.
Повторная комбинация параметров одного шаблона не создаёт ещё одну версию; повтор команды
с прежним Idempotency-Key возвращает прежний результат.

Результат — **черновик** новой версии существующего семейства. Записываются шаблон, значения
параметров и автор генерации. Для выдачи требуется независимая публикация этой версии, а для
code/SQL — существующая проверка и закрепление подходящего набора скрытых тестов в плане.
Старые тесты не копируются автоматически и вариант не считается подкалиброванным.
Отзыв шаблона через `/{template_id}/retire` запрещает новую генерацию; уже выданные версии
сохраняются как самостоятельные закреплённые доказательства.

## Связанные уточнения и история

Задание может содержать `follows_task_key` — ключ более ранней задачи того же семейства.
Самоссылки, ссылки вперёд и на отсутствующую задачу отклоняются. План закрепляет связь, сессия
переводит её в конкретный `parent_stage_id`. Поле `followups` показывает связи и доступность.
До отправки родительского решения API скрывает условие уточнения; раннее создание/чтение его
рабочей среды также запрещено. Запуск уточнения требует отправленного родительского решения
и обычного последовательного перехода этапов. Сохраняются отдельные снимок, доказательства,
рубрика, результаты тестов/LLM и решение проверяющего для каждого этапа.

`GET /v1/assessment-task-history` возвращает только собственные выдачи кандидата: ID сессии,
плана, семейств и версий, дату и статус. Порядок — от новых к старым; `limit` 1–100, `after` — ID
последней строки предыдущей страницы. Чужой курсор возвращает 404. Эталоны и тесты отсутствуют.

Privacy удаляет историю вместе с сессиями и сохранёнными ответами команд, блокируя дальнейшую
выдачу. Авторские/проверяющие записи конфигураций сохраняются с состоянием restricted по
существующим правилам хранения доказательств; конфигурация ограниченного автора не выдаётся.
Выгрузка включает квитанцию выбора, собственные действия и параметры созданных вариантов,
но не раскрывает ещё закрытое уточнение, эталоны и рубрики. Новая миграция — `0017_assessment`.
Приложение проверяет наличие новых таблиц при readiness; populated downgrade запрещён.

## Проверки

Тесты покрывают ротацию семейств и вариантов, историю и курсоры, оба cooldown, скользящие и
глобальные лимиты, конкурентную выдачу, прямой обход, отмену и replay, утверждение независимым
администратором, структурно несовместимые планы, ограниченные параметры и дедупликацию,
закрепление отдельной политики грейда, повреждение квитанции, отзыв конфигурации, Privacy и
отложенное раскрытие уточнений. Отдельный тест использует реальный подписанный обмен
Validation/Assessment и проверяет сохранение исходных скрытых suite pins в выбранной сессии.
Для конкурентного допуска предусмотрен PostgreSQL-тест при наличии
`HR_TEST_ASSESSMENT_DATABASE_URL`; SQLite-сценарий выполняется локально.
