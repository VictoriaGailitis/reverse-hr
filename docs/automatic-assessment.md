# Автоматическая оценка и оригинальные задания

Assessment управляет оригинальными референсами и правилами грейда; Evaluation проверяет доказательства и выставляет баллы. Варианты заданий генерируются из собственных текстов оператора. Импорт и ссылки на внешние банки заданий не предусмотрены.

## Как оценивается результат

1. Сессия закрепляет версии задания, критериев, скрытых тестов, политики и отправленного снимка. Runner получает отдельный подписанный допуск к этому снимку.
2. Баллы за исполняемые критерии берутся только из подписанного результата Runner. LLM не может подтвердить прохождение тестов.
3. Для остальных критериев Evaluation запрашивает два предложения закреплённой модели. Каждое должно ссылаться на реальные строки кода, фрагменты записи или объекты доски. При согласованных предложениях выбираются меньшие баллы по каждому критерию; расхождение более настроенного предела направляется человеку.
4. Assessment принимает автоматическое решение только по утверждённой калиброванной политике с `automatic_decisions=true`. Результаты у границы общего порога или минимума компетенции, недостаточные доказательства и конфликт cooldown требуют человека.
5. Результат имеет происхождение `automatic` или `human`. Автоматический грейд передаётся Candidate и Matching тем же подписанным протоколом, что и решение человека. Доступ компании по-прежнему зависит от согласия и режима доверия к результату.

По умолчанию граница перепроверки — ±5 баллов, выборочная проверка качества — 10%, требуются два предложения LLM с расхождением не более 10% максимума критерия. Настройки модели задаются через `HR_EVALUATION_AUTOMATIC_PROPOSALS` и `HR_EVALUATION_AUTOMATIC_DISAGREEMENT`; порог и выборка — в версии политики грейда. Автоматические политики с критериями LLM обязательно закрепляют модель и digest промпта; смена модели требует новой калибровки. Существующие политики сохраняют прежний ручной режим: для перехода создаётся и утверждается новая политика.

Проверки самостоятельности не снижают баллы компетенций: спорный случай направляется проверяющему. Отсутствие провайдера, неполная транскрипция или недоступность доказательств не дают нулевой результат. Выборочная проверка уже выданного грейда не задерживает доступ кандидата; пересмотр проходит через независимую очередь апелляций с новым человеческим рассмотрением всех этапов. Кандидат может оспорить результат через существующую апелляцию. Если выборочная проверка уже открыта, причина кандидата добавляется в тот же независимый кейс; повторная подача остаётся запрещённой. Исправление публикуется отдельным решением с историей и ссылкой на исходное.

## Референс и пробный вариант

В кабинете администратора есть вкладка «Генерация заданий»; компания использует аналогичный редактор в своём кабинете заданий. Для каждого формата — код, SQL, видео, голос, архитектура/доска — задаются:

- собственное описание, специализация, уровень и длительность;
- обязательные ограничения, разрешённые вариации и запрещённые изменения;
- компетенции, критерии, доказательства и баллы;
- параметры с конечными разрешёнными значениями, размер пула и предел выдач варианта.

Сохранение создаёт черновик. Изменение создаёт новую неизменяемую версию; формат, специализация и уровень принадлежат семейству и меняются через создание другого референса. Политика грейда привязывается отдельно после проверки пробного варианта.

Перед вызовом модели оператор задаёт конкретный сценарий и выбирает параметры. Сервер возвращает спецификацию с digest и сроком 30 минут. Кнопка «Генерировать пробное задание» подтверждает именно эту спецификацию; истёкшее, уже использованное или изменённое подтверждение отклоняется.

Worker резервирует попытку и lease до обращения к провайдеру, проверяет структуру ответа и отдельно запрашивает семантическую проверку. Ответ закреплён за моделью, конфигурацией, промптами и спецификацией; поздний ответ после отзыва референса не публикуется. Проверяется близкое текстовое дублирование, но это не доказательство полной семантической уникальности.

Код и SQL дополнительно требуют эталон, минимум два различных ошибочных решения и скрытые фикстуры. Всё исполняется существующей нативной очередью NsJail на допущенном Linux-узле. До получения подписанного verdict и attestation задание не готово к выдаче. Генерация никогда не исполняет модельный код внутри API или контейнера worker.

Проверенный пробный вариант позволяет утвердить референс платформы другому администратору. Опубликованная версия автоматически пополняет пул; отдельная ручная публикация каждого варианта не нужна. Компания утверждает собственный референс в рамках своего членства; её задания не влияют на общий грейд.

Пул ограничен размером и частотой пополнения; допускается до трёх генераций на место в пуле за час. Для варианта действует общий предел выдач, а для кандидата — сутки между попытками семейства, включая отменённые сессии. Отзыв версии прекращает новую выдачу и отменяет незавершённые генерации. Privacy выгружает авторские данные и удаляет текст/выводы автора, закрывая связанные планы для новых сессий.

## Калибровка и ограничения готовности

Для общего грейда политика утверждается на проверенном пробном плане и содержит `generation_reference_id` конкретной версии. При публикации эта политика переносится на планы вариантов того же референса с отдельными точными pins. Это допуск семейства вариаций, поэтому экспертные данные должны покрывать разрешённую сложность и изменения; сам факт генерации или согласия двух ответов LLM не подтверждает качество шкалы. Новая версия референса требует новой калибровки. Без неё доступны только практика и разрешённая оценка задания компании.

Калибровка загружается в редакторе шкалы или через `POST /v1/grade-policies/{id}/approve`: минимум 20 независимых holdout-примеров, согласованные метки минимум двух экспертов, не менее пяти положительных и пяти отрицательных примеров, точность по каждой группе не ниже политики (обычно 80%). Пример **структуры**, не готовые данные:

```json
{
  "source_digest": "<sha256 набора экспертных результатов>",
  "scoring_version": "competency-weighted-v1",
  "reason": "Описание независимой разметки и состава набора",
  "cases": [
    {
      "case_id": "<uuid примера>",
      "scores": {"primary": 85},
      "labels": [
        {"expert_id": "<uuid эксперта 1>", "passed": true},
        {"expert_id": "<uuid эксперта 2>", "passed": true}
      ],
      "holdout": true
    }
  ]
}
```

Экспертных данных проекта пока нет. Тесты используют явно синтетическую разметку и провайдер; это проверка механизма, не разрешение на промышленное выставление грейдов. Контент и результаты сохраняют существующую маркировку demo; создание оригинального задания не снимает ограничений production Matching.

## Запуск на Linux через Docker

Обычный профиль `all` включает `evaluation-automatic` и `assessment-automatic`. Первый обрабатывает готовые доказательства и создаёт модельные запросы; второй принимает решения по разрешённым политикам. Внешний вызов модели выполняет отдельный `evaluation-llm` из профиля `llm`.

Для генерации задайте в `.env` `ASSESSMENT_GENERATION_ENABLED=true`, точное имя `ASSESSMENT_GENERATION_MODEL` и JSON `ASSESSMENT_GENERATION_CONFIG`. Схема конфигурации — `GatewayConfiguration`: фиксированный HTTPS origin, пределы входа/выхода и размера запроса, тарифы в microUSD за миллион токенов, бюджет `stage_budget_microusd`. Резерв генерации учитывает два вызова на попытку. Бюджет должен покрывать требуемое число попыток; включите запас для JSON-схем Task/SuiteDefinition на входе.

Ключ провайдера хранится только в `.secrets/llm-api-key`, вне Git, с ограниченными правами, как для Evaluation. API Assessment получает публичную конфигурацию, а ключ и внешний network доступны только worker. `ASSESSMENT_TRUSTED_RUNTIMES` должен совпадать с действующим допуском Linux Runner.

```sh
docker compose --profile all --profile llm --profile generation \
  -f compose.yaml -f compose.frontend.yaml up -d --build
```

Для общей LLM-оценки также нужны существующие `EVALUATION_LLM_ENABLED`, `EVALUATION_LLM_MODEL`, `EVALUATION_LLM_CONFIG`. После обновления запустите идемпотентную настройку маршрутов событий из [инструкции Linux](linux-deployment.md): добавлена доставка `assessment.generated_validation_requested.v1` в Runner. Изменение кода Runner меняет fingerprint: перед реальным исполнением повторите probes и утверждение допуска по [инструкции Runner](../infra/runner/README.md).

События содержат только идентификаторы. Эталон, тесты, референс и результаты передаются через подписанные owner API, не через общедоступный брокер. Новые миграции: Assessment `0018_assessment`, Evaluation `0009_evaluation`, Runner `0012_generation`.
