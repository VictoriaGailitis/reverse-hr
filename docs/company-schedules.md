# Подписки, расписания и уведомления заданий компаний

## Подписка кандидата

Сначала кандидат создаёт Privacy consent с purpose `company_task_subscription`.
`PUT /v1/company-task-subscriptions/{organization_id}` принимает `status` (`active`,
`declined`, `cancelled`), `consent_id` только для active и `min_interval_seconds`.
Нужны `Idempotency-Key` и `If-Match` (версия отсутствующей подписки — 1).
Частота по умолчанию — 7 дней; допустимый минимум — сутки, максимум — 90 дней.
Списки и чтение доступны только самому кандидату: `GET /v1/company-task-subscriptions`
и `GET .../{organization_id}`. Список ограничен 50 строками с UUID-параметром `after`.

Каждое изменение подписки увеличивает версию, отменяет прежние расписания,
неотправленные маркетинговые сообщения и ещё не принятые автоматические назначения.
Повторная подписка не восстанавливает прежние действия. Отзыв согласия Privacy
закрывает допуск немедленно при следующей проверке, даже до обработки worker’ом.
Начатая практическая сессия и её служебные сообщения сохраняются при отписке;
отдельные assessment/result-disclosure permissions продолжают проверяться.

Ручное адресное назначение остаётся доступно без подписки; маркетинговое уведомление
о нём требует действующей подписки. Общий частотный предел распространяется на
новые ручные и автоматические назначения одной компании одному кандидату.

## Расписание

Допущенный сотрудник компании создаёт `POST /v1/company-task-schedules` с
`organization_id`, `candidate_id`, `proposal_id`, `plan_version_id`, `starts_at`,
`expires_in_days` и, для повторений, `interval_seconds`/`max_occurrences`.
Предложение должно быть одобрено, а соответствующий план опубликован. Требуется
действующая подписка; интервал не может быть меньше выбранного кандидатом.

`starts_at` требует явный timezone и нормализуется в UTC; старт допустим от минуты
назад до года вперёд. Без интервала допустимо одно назначение; регулярный интервал
от суток до 90 дней, число назначений от 1 до 52. Это фиксированный интервал в
секундах, без календарных правил и коррекции перехода на летнее время.

`GET /v1/company-task-schedules` возвращает собственные расписания кандидата либо
расписания указанной организации для допущенного сотрудника. Список ограничен 50
строками, продолжение через `after`. `GET .../{schedule_id}` показывает состояние;
`GET .../{schedule_id}/jobs` — до 50 действий, сроки, попытки и безопасные коды ошибок.
`POST .../{schedule_id}/cancel` с Idempotency-Key и If-Match отменяет будущие
назначения. Уже выданные назначения сохраняются; для их отказа/отзыва есть API
назначений. Отписка отменяет также ещё не принятые автоматические назначения.

Расписание связано с точной версией подписки. Дубли защищены командной
идемпотентностью, уникальным ключом расписания, уникальными ключами действий,
блокировками субъектов и транзакцией. Просроченные интервалы пропускаются, а не
выдаются пачкой. Активное прежнее назначение того же плана откладывает следующее.

## Доставка и настройки

`PUT /v1/notifications/preferences` поддерживает `in_app` и `marketing_in_app`.
Маркетинг по умолчанию выключен; отсутствие нового поля сохраняет прежнее значение.
`new_assignment` — маркетинг, требует действующей подписки той же версии.
`deadline_reminder` — служебное напоминание за сутки до срока непринятого задания.
`result_ready` — служебное сообщение после проверки всех этапов человеком.
Глобальная настройка `in_app` управляет обоими видами. Уведомления доступны через
существующие list/read endpoints; они содержат assignment ID, вид и категорию,
без ответов, записей, баллов и контактов.

Assessment сохраняет намерение и outbox атомарно. Notification consumer принимает
подписанное `assessment.company_notification_requested.v1`, проверяет подписанный
внутренний `company-notice` API и дедуплицирует доставку. При чтении снова проверяются
текущие разрешения, состояние задания, membership, настройки и актуальные Evaluation
scores. Поздняя доставка после отписки не открывает старое маркетинговое сообщение.
Компания получает сообщение о готовности только при действующем scoped разрешении
на результат; баллы получает через отдельный защищённый result endpoint.

Это уведомления внутри платформы. Email/SMS/push провайдеры и пользовательские
экраны не добавлены.

## Worker и удаление

`python -m reverse_hr.platform.worker company-dispatch` запускается только с Assessment
settings. В Compose предусмотрен `assessment-company-dispatch` (profiles `events`,
`all`), с зависимостями Assessment, Privacy, Employer, Evaluation. Миграции:
Assessment `0014_assessment`, Notification `0003_notification`, Privacy `0008_privacy`.
Readiness проверяет новую схему. Существующий topology generator добавляет маршрут
из Assessment в `notification.incoming`; для работающего RabbitMQ его нужно применить
обычным процессом конфигурации окружения.

Действия хранятся в SQL как pending/done/cancelled. Проверки внешних сервисов не
создают эффектов; транзакция повторно проверяет разрешения и состояние под
блокировками, сохраняет назначение, outbox и состояние действия вместе. При падении
до commit действия выполняются повторно; после commit дубли подавляются.
Временные сбои разрешений повторяются с задержкой до часа; ожидание human review —
каждые пять минут. Попытки, следующий срок и код ошибки видны через jobs API.
Отзыв контента, membership, согласия, подписки и Privacy tombstone отменяет устаревшие
действия. Удаление через Privacy очищает подписки, расписания, лимиты, действия,
источники уведомлений, caches/outbox и сами Notification строки; позднее событие
не восстанавливает удалённые данные. Downgrade защищает непустые таблицы.

Интеграционные проверки: `tests/services/assessment/test_company_schedules.py` — согласия, отказ,
отписка, частота, гонки, повторы, сбои, Privacy, настройки, миграции и уведомления
для проверенных результатов всех пяти форматов. Брокерный маршрут проверяется
генерацией topology во временном каталоге на синтетических credentials.
