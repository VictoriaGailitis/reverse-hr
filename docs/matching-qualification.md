# Подтверждённые компетенции и актуальность квалификации

Код добавляет механизм подбора по результатам проверенных практических компетенций и рекомендации кандидату. Обе новые политики демонстрационные, неподкалиброванные: размеченных данных нет. На реальных кандидатах нельзя считать эти веса утверждённой моделью. Сервер отклоняет `ranking_policy=verified-demo-v1` при `mode=production`. Существующий алгоритм по грейду и заявленным навыкам сохранён как `legacy`; он явно сообщает, что навыки лишь заявлены.

## Происхождение доказательств

Assessment выдаёт в подписанном `/internal/v1/confirmed-grade` optional `qualification`: нормированный итоговый балл 0–100, баллы рубричных компетенций 0–100, минимумы закреплённой политики, дату человеческого решения, policy ID, digest доказательств и сроки повторной попытки/смены грейда. Скрытые тесты, ответы, причины ревьюера и его персональные данные сюда не входят. Это итог человека после оценивания, а не произвольный ответ LLM. Агрегатор суммирует рубричные points/max_points и нормирует по 100; общая оценка следует закреплённым весам GradePolicy.

Подписанное содержимое решения неизменно: срок смены грейда рассчитан из времени данного решения и его закреплённых правил, а не текущего CandidateGrade. Позднейшее решение не изменяет старый receipt. Candidate сохраняет его в existing grade history, выбирает активную ревизию каждого прохождения после апелляции. Для одинакового подтверждённого максимального грейда самое свежее reviewed qualification становится текущим доказательством; профиль получает новую версию. Для старых решений без этих доказательств сохраняется прежняя стабильная привязка.

Опубликованная подписанная CandidateCard содержит доказательство ровно того decision_id, который указан в ней. Новые endpoints подбора используют прежние проверки актуального согласия публикации, ProcessingAccess и компании/потребности. Контакты в Matching не передаются. Отмена публикации, новая ревизия или изменение потребности скрывает устаревшие данные сохранённого результата.

## Поиск и сравнение

`POST /v1/matches` принимает дополнительные поля:

- `ranking_policy`: `legacy` по умолчанию или `verified-demo-v1`;
- `desired_competencies`: до 20 уникальных ключей компетенций;
- `minimum_competency_score`: 0–100, demo default 70;
- `maximum_evidence_age_days`: 1–3650, demo default 365.

Специализация и минимальный грейд обязательны. Required skills текущей подтверждённой потребности должны присутствовать в `qualification.competency_scores` и достигать минимального балла. Одноимённая запись в declared skills этого не заменяет. При текущем интерфейсе required_skills должен содержать именно rubric competency keys; отдельная онтология технологий пока не подключена. Неизвестная обязательная компетенция исключает кандидата. Неизвестная желательная считается отсутствием доказательства и даёт 0, а не LLM предположение.

Demo score = floor((55 × средний балл обязательных и желательных компетенций + 25 × итог Assessment + 15 × актуальность)/100) + achievement bonus. При отсутствии каких-либо компетенций требования считаются выполненными, компонент равен 100. Демоактуальность: ≤180 дней — 100, 181–365 — 50, более 365 — 0. Ограничение evidence age применяется отдельно. Подтверждённые индивидуальные достижения по специализации дают существующий бонус максимум 5; командные и чужой специализации не дают бонуса. Параметры, исходные компоненты, дата расчёта и `verified-competencies-demo-v1` входят в результат. Доказательства и версия кандидата перепроверяются при чтении сохранённого snapshot; расчёт воспроизводится на записанную дату, а истечение максимального допустимого возраста также скрывает кандидата.

`POST /v1/matches/query-preview` принимает organization_id, need_id, text до 4000 символов. Это **ограниченный детерминированный черновик**: он распознаёт только явно упомянутые ключи из требований существующей потребности. Он возвращает текст целиком как неразобранный, authoritative NeedView, предложенный MatchQuery, предупреждения и `requires_employer_confirmation=true`. Ни поиск, ни создание/изменение потребности автоматически не выполняются. Работодатель редактирует и подтверждает потребность через её existing API, затем явно отправляет рассмотренный MatchQuery. Семантический разбор свободного запроса и реальный LLM provider пока не подключены; специализация, зарплата, условия и скрытые требования не выдумываются.

`POST /v1/matches/{snapshot_id}/comparison` принимает 2–10 уникальных candidate_ids из этого snapshot. Сначала перепроверяется весь актуальный snapshot и права владельца. Недоступный/снятый профиль или чужой ID возвращает 404, не раскрывая дополнительные сведения. Ответ содержит те же разрешённые карточки и объяснения.

`POST /v1/matches/{snapshot_id}/refinements` принимает новый рассмотренный MatchQuery. Organization и need ID должны совпадать с исходным поиском; новый результат создаётся под отдельным snapshot ID, исходный расчёт не переписывается. Идемпотентность и актуальная версия потребности проверяются existing command layer.

## Рекомендации кандидату

`GET /v1/candidates/me/qualification` доступен только самому кандидату после текущего ProcessingAccess. Возвращает active revision результатов, их свежесть, сроки и рекомендации. Давно проверенный результат отмечается aging/expired и предлагается повторная проверка; подтверждённый грейд не понижается.

Уровень выше предлагается лишь при подтверждённом текущем грейде, свежем результате, score≥90, всех компетенциях≥80 и одновременном истечении retry/grade-change cooldown. На Lead следующего уровня нет. Более поздняя попытка ограничивает советы из старых результатов своим сроком. Предложение не назначает грейд и не создаёт сессию; настоящий session start по-прежнему проверяет закреплённую политику, предыдущие попытки, согласие и реальные серверные сроки.

Feedback перечисляет конкретные слабые ключи рубрики, фактический балл, целевой минимум и предлагает тренировку/повтор проверенного задания именно по этой компетенции. Минимум берётся из политики; если его нет, target70 помечается неподкалиброванным demo правилом. Общих утверждений «знает SQL» из резюме или рекомендаций внешних непроверенных курсов нет.

## Проверка и эксплуатационные пределы

Новые tests покрывают отсутствие доказательств, недостаточный обязательный балл, отсутствующее желательное доказательство, demo/production, истечение срока без понижения грейда, cooldown, смену active evidence при повторе и апелляции, replay, отзыв публикации, права сравнения/уточнения и immutable signed export после изменения глобального cooldown. Используются actual signed Candidate/Privacy/Hiring RPC и мигрированные отдельные SQLite DB, а основной pipeline Assessment проверяется существующими регрессиями и отдельным signed export тестом.

Новых таблиц, live migration, provider credentials и deploy в этой части нет. Обновлённые поля existing JSON grade history не требуют DDL. Исторические записи без qualification остаются совместимы и не превращаются в подтверждение компетенций. Полноценная semantic/LLM parsing интеграция, калибровка ранжирования и live PostgreSQL/RabbitMQ приёмка остаются отдельными задачами.
